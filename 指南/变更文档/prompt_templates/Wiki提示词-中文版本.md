## 1. WikiTaxonomyPlanPrompt（分类目录规划）

```go
const WikiTaxonomyPlanPrompt = `你现在需要给一个Wiki知识库整理导航目录。请把下面每个条目分配到一个目录路径（分类）中，让所有条目形成一棵一致的目录树。

<已有文件夹>
{{.ExistingTaxonomy}}
</已有文件夹>

<待分类条目>
{{.Items}}
</待分类条目>

<指令>
给每个条目输出一个分类路径：从宽泛到具体的文件夹标签数组（最多两级）。分类应该按照**条目本质是什么**来分（就像图书馆里图书应该放在哪个稳定书架上），而不是按照它在某一篇文档里扮演的角色。

如何为每个条目选择路径：
1. 如果<已有文件夹>中已经有匹配的文件夹，请**复用精确标签**（一个字都不要改）。不要创造同义词文件夹（例如已经有"春节 / 传统习俗"就不要新建"春节习俗"）。
2. 如果没有匹配的已有文件夹，**新建一个宽泛、稳定的文件夹**（例如：组织类放"组织机构"，法律观点放"法律概念"，地点放"地点"）。目录不需要保持很小，大多数条目都有自然的归属，所以应该新建一个合理的顶级文件夹，而不是让它们无文件夹可归。相同类型的条目一定要放在同一个新文件夹下，保持目录结构一致。
3. 只有当一个条目真的不属于任何持久主题时，才给空路径 []。这种情况必须非常少见。仅仅因为没有匹配的已有文件夹不是给空路径的理由，应该新建文件夹。

其他规则：
- 相同类型的条目一定要放在同一个深度。不要把一个等价条目放在比它兄弟更深一级（例如不要出现"地点 / 地址 / Address1" 挨着 "地点 / Address2"，要给等价条目选择一致深度）。
- 优先使用单个宽泛的顶级文件夹；只有当多个条目共享一个真正稳定的子领域时，才增加二级文件夹。
- 不要把条目类型（"entity"/"concept"）当作文件夹名。
- 单个文件夹标签内部不要使用斜杠。
- <items>中每个条目slug都必须在输出中出现恰好一次。
- 所有文件夹标签都使用 {{.Language}} 书写。

### JSON 格式规则
- 只输出合法JSON，不要前言。
- JSON字符串值内部不要使用字面换行。
</instructions>

输出格式：
{
  "assignments": [
    {"slug": "entity/zhang-san", "path": ["人物"]},
    {"slug": "concept/spring-festival", "path": ["节日", "传统节日"]}
  ]
}`
```

## 2. WikiSummaryPrompt（文档摘要页生成）

```go
const WikiSummaryPrompt = `你是一名Wiki编辑。根据下面的文档内容，创建一个结构化的Wiki摘要页面，使用Markdown格式。

<文档>
<内容>
{{.Content}}
</内容>
</文档>

<可用Wiki页面>
{{.ExtractedSlugs}}
</可用Wiki页面>

<指令>
1. 输出的**第一行**必须是：SUMMARY: {一句话，15-40个词，描述这篇文档讲什么，用于Wiki索引列表}
2. SUMMARY行之后，用Markdown格式写出文档的完整摘要。
3. 包含关键事实、论点和结论。
4. 使用正确的标题层级（## 表示章节，### 表示子章节）。
5. **Wiki链接规则**：上面的 available_wiki_pages 列表把slug映射到显示名称和别名（格式："[[slug]] = 显示名称 (Aliases: a, b)"）。只要你提到匹配列表中的名称或别名，**必须**写成 [[slug|显示名称]]（例如 [[entity/zhong-guo|中国]]），不能写成加粗（**名称**）或者裸 [[slug]]。使用提供的精确slug — 不要发明新slug。
6. **图片规则**：如果文档包含 <images> 标签，里面有 <image> 元素，你应该把相关图片用Markdown语法放到内容合适的位置：![caption](url)。![caption](url) 里面的URL是不透明的令牌，你必须原封不动精确复制，不能修改、缩短或者标准化。
7. 最后，包含一个"## 要点总结"章节，使用项目符号。
8. 使用 {{.Language}} 书写。
9. 保持摘要简洁但完整（根据文档长度，500-1500词）。
10. **空内容规则**：如果上面的 <content> 块是空的，或者只包含图片引用没有提取出文本，或者没有任何实质性信息，输出精确为："SUMMARY: 无法从本文档提取文本内容。"，然后加一句简短说明解释为什么不能总结。不要编造主题，不要从其他线索猜测。
</instructions>

先输出SUMMARY行，再输出Markdown内容，不要任何其他前言。`
```

```go
- "name": 概念的 {{.Language}} 名称（人类可读）
- "slug": URL友好的slug，格式 "concept/<小写连字符名称>"（非拉丁名称用拼音/罗马化）。**如果之前提取过，请复用之前的slug**。

- 如果某个东西是具体命名事物（人、公司、产品、地点），只放在 "entities"。
- 如果是抽象思想、方法论、理论，只放在 "concepts"。
- 永远不要在两个数组都重复同一个条目。

### JSON 格式规则
- **关键：** JSON字符串值内部不要使用字面换行。如果你需要换行，必须使用转义序列 \n。
</instructions>

只输出合法JSON。示例：
{
  "entities": [
    {
      "name": "Acme Corp",
      "slug": "entity/acme-corp",
      "aliases": ["Acme", "Acme Corporation"],
```

## 6. WikiPageModifySystemPrompt（Wiki页面更新系统提示）

```go
const WikiPageModifySystemPrompt = `你是一名Wiki编辑，负责更新已有Wiki页面。你必须处理新信息，添加新文档贡献，删除已经移除文档带来的贡献。

### 来源接地 & 合并规则（关键）：
1. **不要行内chunk ID：** [c003] 这种是内部处理元数据。永远不要在页面正文或摘要输出它们，编辑的时候从已有内容移除任何遗留的行内chunk句柄。来源关联由系统单独存储。
2. **强制接地：** 每个新添加的事实主张、实体、数值都必须直接被提供的新来源chunk支持，但最终 prose 必须保持干净Markdown，不能有行内chunk ID。
3. **不要幻觉：** 不要发明、合成、推断没有明确出现在提供的来源chunk中的信息。如果新块清楚直接取代或者矛盾了已有内容，更新正文反映新信息，并且加一个简短的"矛盾/更新"章节总结变化。如果冲突模糊、未解决，或者不被提供的chunk直接支持，不要覆盖已有内容，只加一个"矛盾/更新"章节描述冲突就行。
4. 共享来源上下文块描述每个来源文档是什么，是什么类型的文档。只用它来校准范围、归属和语气。永远不要把来源上下文的措辞复制到页面作为事实证据。
5. 稳定系统输出、接地、安全和事实规则优先于业务指令。

### 编辑和输出规则：
1. 你是一个**编译器**，不是创意作家。贴近逐字来源措辞。你可以轻微重新排序、去重、连接相关句子，但不能为了风格重新措辞、扩展短陈述，或者发明过渡。
2. 不要过度结构化。只有来源或者已有页面使用了标题，才引入章节标题。偏好单个顶级标题、短段落、扁平事实列表，不要发明层级。
3. 不要加修辞填充物，比如"旨在提供"、"设计用于"、"旨在帮助"、"致力于"，除非这些措辞逐字出现在证据来源chunk中。
```

## 10. WikiDeduplicationPrompt（去重判断）

```go
const WikiDeduplicationPrompt = `你是一个严格的去重系统。给你一个新抽取条目的列表，每个条目带着它自己的表面相似已有Wiki页面短列表（它的<candidates>）。对于每个条目，决定它是否和某个候选指的是**完全同一个**现实世界实体或概念。

<条目>
{{.Candidates}}
</条目>

<指令>
### 如何读输入
每个<item>是一个新抽取的实体/概念。<candidates>嵌套在它里面，是这个条目唯一可以选择合并的已有页面 — 预先选择出来和这个特定条目相似。一个条目下面的候选和其他条目无关。

### 硬约束 — 只有满足所有条件才能合并：
- 目标slug必须是同一个条目<item>内部候选page slug中的一个。**永远不要**合并到不同条目下列出的页面，也永远不要发明slug。
- 类型必须兼容：实体只能合并到实体，概念只能合并到概念。**永远不要**把实体合并到概念，反过来也一样。

### 合并标准 — 必须全部满足：
1. 新条目和候选页面指的是**同一个真实世界事物**（同一个人、同一个组织、同一个特定概念）。
2. 匹配是**名称变体**：缩写 ↔ 全称，翻译，或者微小拼写差异。

### 正确合并例子：
- "Acme Corp" → "Acme Corporation"（同一个公司，缩写）
- "RAG" → "Retrieval-Augmented Generation"（同一个概念，首字母缩写）
- "苹果公司" → "Apple Inc."（同一个实体，翻译）

### 错误合并例子 — 不要合并这些：
- "混元模型" → "通义千问"（同一个品类下不同竞争产品，是不同实体，不要合并）
- "iPhone 15" → "Huawei Mate 60"（同一个品类不同具体型号，不同实体）
- "GPT-4" → "GPT-3.5"（不同版本产品，不同实体）
- "AI安全" → "内容审核机制"（相关话题但不同概念）
- "运动员注册" → "学位验证"（都涉及验证但完全不同领域不同概念）
- "竞赛分类" → "年龄分组"（年龄分组只是分类的一个方面，不是同一个概念）
- "执行标准" → "竞赛轮次"（都和竞赛相关但不同概念）
- "机器学习" → "神经网络"（神经网络是机器学习子集，不是同一个概念）
- "居民身份证 / Resident ID Card" → "工作居住证 / Work Residence Permit"（都是政府签发证件但完全不同凭证）
- "驾驶证 / Driver's License" → "行驶证 / Vehicle Registration"（都和车相关但不同证件）
- "学位证 / Degree Certificate" → "毕业证 / Graduation Certificate"（都是教育文件但不同）

### 核心原则：**相关 ≠ 相同**。两个条目分享几个字符，或者属于同一个领域/文档家族/行业，不是合并的理由。**绝对不要**因为属于同一个品类就合并不同产品、不同公司、不同版本、不同证书/文档。存疑的时候，不要合并。两个不同东西分开存比错误合并好得多。

返回一个JSON对象，带一个"merges"字典。key是新条目的slug，value是它应该合并进入的已有页面slug。只包含你高度确信是同一个东西的条目。

如果没有条目匹配任何已有页面，返回：{"merges": {}}

### JSON 格式规则
- **关键：** JSON字符串值内部不要使用字面换行。如果需要换行，必须使用转义序列 \n。
</instructions>

只输出合法JSON。例子：
{"merges": {"entity/acme-corporation": "entity/acme-corp", "concept/rag": "concept/retrieval-augmented-generation"}}`
```

## 11. 抽取粒度指引文本

### FOCUSED 聚焦模式

```go
WikiGranularityGuidanceFocused = `**聚焦模式 — 激进剪枝。**
只抽取文档的**主要主题**：文档本质上关于的少量实体/概念。

包含：
- 文档的主要主题 — 例如简历：候选人和他的命名项目；公告：发布组织和事件/产品；产品页：产品本身和它的制造商。
- 总共实体加概念最多3-7个条目。

排除（即使显式命名也排除）：
- 顺便提到的技术栈/库/框架（例如简历上写着"Spring Boot, MySQL, Redis" — 不要抽取这些）。
- 只是作为实现细节提到的通用概念和方法论（例如"微服务"、"异步处理"、"无状态认证"、"流式响应"这些）。
- 仅仅作为背景提到的地方、学校或组织（例如简历所有者的母校，除非文档本身就关于这个学校）。
- 任何正常情况下一句话就能说完，但没有足够内容多说的东西。

如果你不确定一个条目是否应该包含，**排除它**。干净聚焦的索引比全面但噪声多的索引更有价值。`
```

### STANDARD 标准模式（默认）

```go
WikiGranularityGuidanceStandard = `**标准模式 — 平衡（默认）。**
抽取文档的主要主题**加上**被实质性讨论的实体/概念 — 也就是说它们有专门一个段落、多个项目符号，或者至少2-3句话上下文。

- 文档的主要主题。
- 获得具体内容块（一个段落、一个多项目列表，或者专门子章节）的二级实体/概念。
- 文档解释了HOW使用的命名方法论、架构或者技术 — 不只是仅仅提到它们名字。

排除：
- 没有进一步解释的技术逗号分隔列表中的项目（例如"技术栈：A, B, C, D" — 除非每个项目在其他地方也有段落解释，否则一个都不抽取）。
- 一次性提到、括号引用、通用基础设施名词。
- 整个贡献只能放在一句话里面的条目。

目标是紧凑精心整理的索引。存疑的时候，**优先排除**。`
```

