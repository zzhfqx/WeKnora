## 第一章：先搞懂 MCP 是什么

### 1.1 一句话解释 MCP

**MCP = Model Context Protocol（模型上下文协议）**，简单说就是：

> 一套让 AI 大模型（比如 Claude、GPT）能**调用外部工具**的通用"插座标准"。

### 1.2 打个比方

就像 USB 接口——不管你是 U 盘、鼠标、键盘，只要是 USB 接口，插到电脑上就能用。

- **MCP 客户端** = 电脑（比如 Claude Desktop、OpenCode、DSH、Cursor）
- **MCP 服务端** = USB 设备（WeKnora 提供的工具）
- **MCP 协议** = USB 标准（规定了怎么说话、怎么传数据）

### 1.3 WeKnora 为什么要做 MCP？

WeKnora 本身是一个知识库 + Agent 平台。有了 MCP，其他 AI 工具（比如 Claude）就能直接：

- 🔍 搜你的知识库
- 📖 读你的文档
- 💬 调用你的 Agent 聊天
- 📚 查询 Wiki
- ...等等

这样你在任何支持 MCP 的 AI 客户端里，都能用 WeKnora 的能力，不用来回切页面。

## 第三章：内置 MCP Server（官方推荐 ✅）

### 3.1 是什么？

**内置 MCP Server** 是 WeKnora 后端服务自带的 MCP 接口，用 Go 语言写的，和主程序一起启动。

- 🏠 **就长在 WeKnora 服务里**，不用额外安装任何东西
- 🌐 **走 HTTP 协议**，远程也能访问
- 🔐 **每个端点一个专属 Token**，安全性高
- 🎯 **v0.8.2 推出**，是官方现在主推的方案

### 3.2 有多少工具？

**一共 12 个工具**，分四大类：

#### 📚 第一类：检索工具（5个）—— 查知识库用


| 工具名                 | 中文名叫啥 | 一句话说清楚                     |
| ---------------------- | ---------- | -------------------------------- |
| `list_knowledge_bases` | 列出知识库 | 看看你有哪些知识库               |
| `search_knowledge`     | 搜索知识   | 用关键词搜知识库，返回相关片段   |
| `grep_chunks`          | 片段搜索   | 在指定知识库搜字面量（精确匹配） |
| `list_documents`       | 列出文档   | 看看某个知识库里有哪些文档       |
| `read_document`        | 读取文档   | 读整篇文档，支持分页和关键词定位 |

#### 💬 第二类：聊天工具（1个）—— 跟 Agent 对话


| 工具名 | 中文名叫啥 | 一句话说清楚                      |
| ------ | ---------- | --------------------------------- |
| `ask`  | 提问       | 调用端点配置的默认 Agent 回答问题 |

> 💡 注意：`ask` 工具**不能选 Agent**，只能用这个 MCP 端点绑定的那个默认 Agent。这是安全设计，防止 AI 乱调其他 Agent。

#### 📖 第三类：Wiki 工具（3个）—— 查 Wiki 用


| 工具名           | 中文名叫啥     | 一句话说清楚                 |
| ---------------- | -------------- | ---------------------------- |
| `wiki_search`    | 搜索 Wiki      | 搜 Wiki 里的内容             |
| `wiki_read_page` | 读取 Wiki 页面 | 读一整页 Wiki 内容           |
| `wiki_index`     | 索引 Wiki      | 让 Wiki 重新建索引（管理用） |

#### ✏️ 第四类：写入工具（3个）—— 改知识库（默认关闭）


| 工具名            | 中文名叫啥 | 一句话说清楚       |
| ----------------- | ---------- | ------------------ |
| `add_document`    | 新增文档   | 往知识库里加新文档 |
| `update_document` | 更新文档   | 修改已有的文档     |
| `delete_document` | 删除文档   | 删掉某篇文档       |

> ⚠️ 这三个默认是关的，要在管理后台手动开启。毕竟让 AI 随便删东西挺危险的。

### 3.3 怎么用？

#### 第一步：找到 MCP 端点

在 WeKnora 管理后台，找到"MCP 端点"或"集成设置"之类的页面，你会看到：

- **端点 URL**：类似 `http://你的服务器地址/api/mcp/xxx`
- **认证 Token**：以 `mcp_` 开头的一串字符

#### 第二步：用 Postman 测试（新手推荐）

发个请求看看有哪些工具：

```http
POST /api/mcp/你的端点名
Host: 你的服务器地址
Authorization: Bearer mcp_你的token
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list"
}
```

成功的话，你会收到 12 个工具的列表。

#### 第三步：调用一个工具试试

比如搜索知识库：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "search_knowledge",
    "arguments": {
      "query": "大模型是什么",
      "knowledge_base": "我的知识库名称"
    }
  }
}
```

#### 第四步：接入 AI 客户端

比如 Claude Desktop，在配置文件里加：

```json
{
  "mcpServers": {
    "weknora-builtin": {
      "transport": "streamable-http",
      "url": "http://你的服务器/api/mcp/你的端点",
      "headers": {
        "Authorization": "Bearer mcp_你的token"
      }
    }
  }
}
```

重启 Claude，就能在对话里直接用 WeKnora 搜知识库了。

### 3.4 适合谁用？

- ✅ 想把 WeKnora 能力集成到第三方平台（DSH、OpenCode 等）
- ✅ 团队多人共用一个知识库
- ✅ 服务器部署，需要远程访问
- ✅ 追求安全性（专属 Token 权限隔离）

### 3.5 权限控制（三层防护，开箱即用）

很多人关心：MCP 端点给出去了，会不会乱调？会不会看到不该看的知识库？

放心，官方设计了**三层权限控制**，每层都是独立的，你可以按需配置。

#### 第一层：工具白名单——哪些工具能用？

每个 MCP 端点可以独立配置「允许调用哪些工具」。

- 没开启的工具，在 `tools/list` 里根本看不到
- 就算客户端猜到工具名，硬调也会被拒绝

打个比方：就像饭店的菜单——你没点的菜，菜单上不印，你说菜名也不给做。

**源码原理**（`internal/mcpserver/server.go`）：

```
filterTools  →  控制 tools/list 能看到哪些工具（第一道门）
guardTool    →  每次 tools/call 都检查白名单（第二道门）
```

两道门同时防，安全系数拉满。

#### 第二层：知识库范围——能看哪些知识库？

每个 MCP 端点可以指定「只能访问哪些知识库」。

- 配置了白名单 → 只能用列表里的知识库
- 没配置 → 能用整个工作区的所有知识库

而且就算你在参数里传了不在范围内的知识库 ID，调用也会报错，不会泄露数据。

打个比方：就像进了图书馆，但你只能进指定的几个阅览室，别的阅览室门都不让你进。

**源码原理**（`internal/mcpserver/scope.go`）：

```
allowedKnowledgeBases()  →  算出这个端点能碰哪些知识库
selectKnowledgeBases()   →  请求的知识库和允许的做交集，不在范围内直接拒绝
knowledgeInScope()       →  读文档时再确认一次文档属于允许的知识库
```

#### 第三层：速率限制——每分钟能调多少次？

每个端点可以独立配置**每分钟最多调用多少次**，默认是 60 次/分钟。

防止程序 bug 或者恶意调用把服务打爆。

打个比方：就像自助餐限时 2 小时，你不能一直吃个不停。

### 3.6 二次开发：按用户控权（4 种改造方案）

你可能会问：**能不能做到「不同用户连同一个 MCP 端点，看到的东西不一样」？**

比如：

- 用户 A 连过来 → 只能看知识库 1、2，能用 3 个工具
- 用户 B 连过来 → 能看知识库 3，能用全部工具

**答案是：可以，而且有 4 种方案，从简单到复杂，你按需选。**

#### 先搞懂：官方现在的鉴权逻辑是什么样的？  

在讲改造方案之前，先看看官方现在是怎么鉴权的（`internal/middleware/mcp_endpoint_auth.go`）：

```
客户端请求
    ↓
从 URL 路径拿到 endpoint_id
从 Authorization Header 拿到 Bearer Token (mcp_xxx)
    ↓
验证 Token 对不对 → 查出端点信息
    ↓
构造一个"虚拟用户"（ID 是 mcp-端点ID，不是真实用户）
    ↓
把虚拟用户塞到请求上下文里
    ↓
后面所有工具调用都用这个虚拟用户的身份
```

**关键点：现在是「端点 Token = 身份」，不是真实用户。** 同一个端点，谁拿到 Token 谁就是同一个身份。

所以如果你想按真实用户控权，就要在这个流程里加东西。

---

#### 方案 A：Header 传用户 ID（最简单，快速验证用）

**思路**：在请求 Header 里加一个 `X-User-ID`，中间件里读到以后，查真实用户信息，替换掉虚拟用户。

```
客户端请求
    ↓
原来的：端点 Token → 虚拟用户
现在的：端点 Token + X-User-ID → 真实用户
```

**改哪里**：就一个文件 `internal/middleware/mcp_endpoint_auth.go`

```go
// 伪代码示意
func MCPEndpointAuth(...) gin.HandlerFunc {
    return func(c *gin.Context) {
        // ... 原来的端点验证逻辑不变 ...
      
        // === 你加的代码 ===
        userID := c.GetHeader("X-User-ID")
        if userID != "" {
            realUser, _ := userService.GetUserByID(ctx, userID)
            // 把真实用户塞到上下文里
            applyAuthSession(c, authSession{
                User: realUser,
                Role: realUser.Role,
                // ...
            })
            return
        }
        // === 加到这里结束 ===
      
        // 原来的虚拟用户逻辑
        applyAuthSession(c, authSession{
            User: virtualUser,
            // ...
        })
    }
}
```


| 项目         | 评价                                            |
| ------------ | ----------------------------------------------- |
| **改代码量** | 很小（1 个文件，十几行）                        |
| **灵活度**   | 中等（能区分用户）                              |
| **安全性**   | ⚠️ 要自己保证 Header 不被伪造（比如再加签名） |
| **推荐指数** | ⭐⭐⭐（适合内部系统、快速验证）                |

---

#### 方案 B：每个用户一个端点（零代码！官方原生支持）

**思路**：不用改一行代码！官方设计就是「一个端点 = 一套权限」。你给每个用户单独创建一个 MCP 端点，分别配置好工具和知识库范围，然后把 Token 发给对应的人。

```
用户 A → 端点 A（Token A）→ 知识库 1、2，3 个工具
用户 B → 端点 B（Token B）→ 知识库 3，全部工具
用户 C → 端点 C（Token C）→ ...
```


| 项目         | 评价                           |
| ------------ | ------------------------------ |
| **改代码量** | 零！完全不用改                 |
| **灵活度**   | 高（每个用户独立配置）         |
| **安全性**   | 🔒 最高（官方原生设计）        |
| **管理成本** | 用户多的时候，端点管理有点麻烦 |
| **推荐指数** | ⭐⭐⭐⭐⭐（用户不多时首选）   |

> 💡 **什么时候选这个方案？**
>
> 用户数量不多（比如十几个、几十个），或者你愿意写个小脚本自动管理端点 → 选这个，最省事最安全。

---

#### 方案 C：动态权限中间件（最灵活，推荐二次开发）

**思路**：在工具调用的入口（`guardTool`）加一层自定义逻辑，根据用户 ID 动态判断：

1. 这个用户能不能调这个工具？
2. 这个用户传的参数合不合法？（比如只能搜指定知识库）

**改哪里**：`internal/mcpserver/server.go` 的 `guardTool` 函数

```go
// 伪代码示意
func (s *Server) guardTool(next server.ToolHandlerFunc) server.ToolHandlerFunc {
    return func(ctx context.Context, req mcp.CallToolRequest) (*mcp.CallToolResult, error) {
        ep, _ := endpointFromContext(ctx)
      
        // === 你加的第一关：用户能不能调这个工具？===
        userID := 从请求上下文拿用户ID(ctx)
        if !用户有权限调工具(userID, req.Params.Name) {
            return mcp.NewToolResultError("你没有权限用这个工具"), nil
        }
      
        // === 你加的第二关：参数级过滤 ===
        // 比如用户只能搜指定知识库，就把参数里的知识库替换/过滤掉
        filteredReq := 过滤参数(req, userID)
      
        // 原来的白名单检查不变
        if !ep.HasTool(filteredReq.Params.Name) {
            return mcp.NewToolResultErrorf("tool not enabled"), nil
        }
      
        // 往下走
        return next(ctx, filteredReq)
    }
}
```


| 项目         | 评价                                   |
| ------------ | -------------------------------------- |
| **改代码量** | 中等（2-3 个文件）                     |
| **灵活度**   | 🔧 最高（工具级 + 参数级都能控）       |
| **安全性**   | 高（你自己写的逻辑自己说了算）         |
| **推荐指数** | ⭐⭐⭐⭐（用户量大、需要精细控制时选） |

> 💡 **这个方案能做到什么程度？**
>
> 举几个例子：
>
> - 用户 A 调 `search_knowledge` → 自动只能搜「部门 A 的知识库」
> - 用户 B 调 `read_document` → 只能看自己上传的文档
> - 访客角色 → 只能用检索工具，不能用 `ask` 聊天工具
> - 等等...只有你想不到，没有做不到

---

#### 方案 D：JWT + 端点双认证（最正规，适合做 SaaS）

**思路**：把认证方式改成「MCP 端点 Token + JWT」双层认证：

- **端点 Token**：决定这个端点能用哪些工具、哪些知识库（粗粒度）
- **JWT**：确定当前是哪个用户（细粒度）

然后两者取交集——用户能看到的 = 端点允许的 ∩ 用户有权的

```
客户端请求
    ↓
Authorization: Bearer mcp_xxx    →  验证端点（工具范围 + KB 范围）
X-JWT-Token: eyJhbGciOiJIUzI1...  →  验证用户（身份 + 角色）
    ↓
两者取交集 → 最终权限
```


| 项目         | 评价                           |
| ------------ | ------------------------------ |
| **改代码量** | 大（中间件、认证逻辑都要改）   |
| **灵活度**   | 🔧 最高最正规                  |
| **安全性**   | 🔒 最高                        |
| **推荐指数** | ⭐⭐⭐（做对外 SaaS 服务时选） |

---

### 3.7 方案选择建议（决策指南）

不知道选哪个？照着下面选就对了：

```
你的用户有多少？
│
├─ 少于 20 人 ──────────────────────────► 方案 B（每个用户一个端点，零代码）
│
├─ 20~100 人，需要精细控制 ─────────────► 方案 C（动态权限中间件）
│
├─ 只是快速验证一下，内部系统用 ────────► 方案 A（Header 传用户 ID）
│
└─ 做 SaaS 产品，对外服务大量用户 ─────► 方案 D（JWT + 端点双认证）
```

### 3.8 一句话总结

> **内置 MCP Server 本身就有三层权限控制（工具白名单 + 知识库范围 + 速率限制），
> 想按用户控权也完全没问题——二次开发很方便，架构上预留了扩展点，
> 最简单的方案甚至不用改代码（每个用户一个端点）。**

## 第四章：CLI MCP Server（本地开发用）

### 4.1 是什么？

**CLI MCP Server** 是 WeKnora 命令行工具（`weknora`）里带的一个 MCP 服务，在你**本地电脑**上运行。

- 💻 **本地运行**，通过命令行启动
- 📺 **走 stdio 模式**（标准输入输出），适合本地 IDE
- 🔗 **本质是个"翻译官"**——把 MCP 请求翻译成后端 API 调用
- 🛠️ **10 个工具**，都是常用的读写操作

### 4.2 有多少工具？

**一共 10 个工具**：


| 工具名          | 中文名叫啥 | 一句话说清楚               |

### 4.3 怎么用？

## 第五章：Python MCP Server（已弃用 ⚠️）

### 5.1 是什么？

**Python MCP Server** 是 WeKnora 早期用 Python 写的 MCP 服务，是最早的一套 MCP 方案。

- 🐍 **Python 实现**，单独一个 `mcp-server/` 目录
- 📦 **31 个工具**，数量最多
- ⚠️ **v0.8.2 起官方宣布弃用**，不推荐新用户使用
- 📜 还在源码里，但不会有新功能了

### 5.2 有多少工具？

**一共 31 个工具**，分几大类：

#### 🔍 知识库管理（多个）

- `list_knowledge_bases`、`get_knowledge_base`、`create_knowledge_base`、`delete_knowledge_base`
- 增删改查全齐了

#### 📄 文档管理（多个）

- `list_documents`、`get_document`、`upload_document`、`delete_document`
- 上传、删除、查看都有

#### 🔎 检索工具（多个）

- `hybrid_search`（混合搜索）
- `search_chunks`（语义搜索）
- `list_chunks`（列片段）
- ...等等

#### 💬 聊天/Agent（多个）

- `chat`、`agent_chat`、`session_chat`
- `list_agents`、`get_agent`
- 各种聊天方式

#### 📊 其他杂项

- 还有一些统计、配置类的工具

### 5.3 为什么被弃用？

1. **维护成本高**：Python 一套、Go 一套，两边功能重复，维护起来累
2. **部署麻烦**：要装 Python 环境、装依赖，不如内置的方便
3. **工具太杂**：31 个工具很多功能重叠，用户也懵
4. **官方重心转移**：主力开发内置 MCP Server，Python 版慢慢就停了

### 5.4 还能用吗？

- 能用，但**不推荐**
- 如果你之前已经在用了，可以继续用，但不会有新功能更新
- 新项目直接用内置 MCP Server 就好

### 5.5 适合谁看？

- ⚠️ 维护老项目的人
- ⚠️ 想研究 WeKnora MCP 演进历史的人
- ❌ 新手别从这个开始学

## 第七章：常见问题 FAQ

### Q1：内置 MCP Server 的 Token 是 JWT 吗？

**不是。** 是独立的 MCP 端点 Token，以 `mcp_` 开头。

- JWT 是用户登录用的，有时效
- API Key 是全局的，能调所有接口
- MCP Token 是**每个端点一个**，只能用在这个 MCP 端点上，权限最小化

> 就像大门钥匙（API Key）和工具箱钥匙（MCP Token）的区别——工具箱钥匙只能开工具箱，丢了也不怕。

### Q2：内置 MCP 的 `ask` 工具为什么不能选 Agent？

**安全设计。** MCP 客户端（AI）不能随便选 Agent，只能用这个端点绑定的默认 Agent。

这样管理员可以控制：这个 MCP 端点只能用某个 Agent，防止 AI 越权调用。

### Q3：Agent 检索工具合并对 MCP 有影响吗？

**对 MCP 接口没影响。** 解释一下：

- Agent 内部工具合并（旧 4 个 → 新 3 个）是**底层**的变化
- MCP 工具是**对外的接口**，接口没变
- 就像饭店换了厨师，但菜单还是那些菜——你吃的东西没变，只是后厨做法变了

具体来说：

- 直接检索工具（`search_knowledge`、`grep_chunks` 等）：完全不受影响
- 聊天工具（`ask`）：底层用了新的 Agent 工具，效果可能更好，但你调用方式不变

### Q4：为什么 Python MCP 弃用了还在源码里？

**弃用 ≠ 删除。**

- 弃用 = 不推荐用了、不更新了
- 但为了兼容老用户，暂时还留着
- 可能未来某个大版本会删掉，但 v0.8.3 还在

### Q5：三套 MCP 可以同时用吗？

**可以。** 它们互不影响：

- 内置 MCP：服务端开着就行
- CLI MCP：你本地装了 CLI 就能用
- Python MCP：你跑起来就能用

三个可以同时存在，各用各的。

### Q6：MCP 和 REST API 是什么关系？

MCP 和 REST API 是**两条平行的路**，都能调用 WeKnora 的能力：


| 对比         | MCP                   | REST API              |
| ------------ | --------------------- | --------------------- |
| **给谁用**   | AI 大模型（自动调用） | 人 / 程序（手动调用） |
| **协议**     | JSON-RPC 2.0          | HTTP REST             |
| **发现能力** | 自动列出工具列表      | 自己看文档            |
| **交互方式** | AI 自己决定调哪个     | 你写代码指定调哪个    |

> 简单说：**MCP 是给 AI 用的 API，REST API 是给人写代码用的 API。**

### Q7：内置 MCP Server 的写入工具为什么默认关闭？

**安全考虑。**

让 AI 能读你的知识库没问题，但让 AI 能随便删文档、改文档，风险就大了。万一 AI 理解错了你的意思，把重要文档删了怎么办？

所以写入工具默认是关的，你确认需要再手动开。

### Q8：`read_document` 怎么用？有两种模式？

是的，`read_document` 有两种用法：

1. **分页模式**（`offset` + `limit`）：一页一页读整篇文档
2. **文内查找模式**（`query` 关键词）：在文档里搜关键词，返回命中位置和上下文

就像看书——分页模式是按页码翻，文内查找是 Ctrl+F 搜关键词。
