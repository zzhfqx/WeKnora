> 基于 kb-regscene-demo-003 / kb-regscene-demo-004 知识库建设过程中的踩坑与最佳实践整理
> 日期：2026-09-26

## 一、总体架构

### 1.1 v3 双体系融合架构

v3 不再是纯自底向上的三层本体，而是**双体系融合**架构：

- **自底向上**：法规场景本体（法规 / 条款 / 业务对象）—— 从文档出发，细粒度拆解
- **自顶向下**：主题分类目录（保险 / 金融监管 / 意外险监管 / 税收优惠 / 责任转换业务 等）—— 从参考库继承的主题概念树

两套目录体系**共存于同一个知识库，通过 wiki 链接互链，而不是互相替代**。用户既可以按"法规→条款→业务对象"的文档视角浏览，也可以按"保险监管→意外险监管→具体主题"的主题视角浏览，两者通过 wiki 链接互相跳转。

### 1.2 顶层目录从 3 个扩展到 9 个

```
一级目录（9个，顶层文件夹）
  ├── 业务对象        （v2 原有）
  ├── 保险           （参考库新增，主题分类根节点）
  ├── 保险指标        （参考库新增）
  ├── 保险监管        （参考库新增）
  ├── 意外险          （参考库新增）
  ├── 意外险监管       （参考库新增）
  ├── 条款           （v2 原有）
  ├── 法规           （v2 原有）
  └── 金融监管        （参考库新增）
```

| 维度 | v2 | v3 | 增长 |
|------|----|----|------|
| 页面总数 | 272 | 349 | +77 |

### 1.4 页面类型与 Tab 对应关系

| 前端Tab | 包含的 page_type | 本项目中的用途 |
|---------|-----------------|--------------|
| 知识     | entity + concept + synthesis + comparison | 法规详情页、条款页、业务对象页（entity）+ 主题概念页（concept） |
| 摘要     | summary | 精简摘要页（11篇，平铺展示，无目录树） |

**重要：** v2 全部用 `entity` 类型；参考库大量使用 `concept` 类型（主题概念）。合并后两种类型共存，都显示在"知识"Tab下，不影响浏览体验。

## 三、知识库合并（Merge）方法论

### 3.1 合并前的分析步骤

合并两个知识库之前，必须先做充分的分析，不能直接导数据：

1. **导出双方数据**：分别导出 v2 本体库和参考库的 pages、folders、relations
2. **分析 slug 冲突**：两个库的 slug 是否有重复
3. **分析死链**：v2 中哪些 wiki 链接指向的 slug 在 v2 中不存在（指向参考库的概念）
4. **制定合并策略**：确定合并顺序、冲突处理方式、索引页重建方案

### 3.2 零 slug 冲突是合并前提

**分析结论：** v2 的 slug 前缀和参考库的前缀虽然有重叠（都用 `entity/`），但实际内容完全不重叠：

- v2 的 `entity/` 前缀：条款（`entity/clause-xxx`）、法规详情页（`entity/regulation-xxx`）、业务对象（`entity/xxx`）
- 参考库的 `entity/` 前缀：主题概念实体（如保险公司、保险产品等）
- 参考库还有 `concept/` 前缀：主题概念分类

**实际结果：零冲突。** 因为 v2 聚焦的是"个税法/意外险责任转换"这个具体场景下的条款和 BO，而参考库的 entity 是通用保险概念，命名空间完全不重叠。

> ⚠️ **如果有冲突怎么办？** 先在其中一个库里把冲突的 slug 重命名（同步更新 content 中的 wiki 链接和 relations 表），再合并。重命名策略：加前缀或加后缀区分。

### 3.3 死链修复

v2 中大约有 **165 个** wiki 链接指向主题概念（如"[[entity/人寿保险|人寿保险]]"），这些 slug 在 v2 库中不存在，是死链。

合并后，因为参考库的主题概念页面被导入了，这些死链**自动变为有效链接**，无需手动修复。

这也是为什么要做双体系融合的核心原因之一 —— v2 的法规条款内容里天然引用了大量通用保险概念，只有把参考库的主题分类导进来，这些链接才能真正连通。

### 3.4 合并执行顺序

**严格按以下顺序执行，不能乱：**

```
Step 1: 复制 v2 全部数据到新 KB
        ├── wiki_folders（全部文件夹）
        ├── wiki_pages（全部页面：法规/条款/BO/摘要/索引）
        └── wiki_page_relations（全部关系）

Step 2: 导入参考库的 folders 和 pages
        ├── 先导入 folders（注意 parent_id 映射）
        └── 再导入 pages（entity + concept 类型的主题概念页）
        （跳过 summary 和 index 类型，保留 v2 的摘要和索引）

Step 3: 导入参考库的 relations
        └── 只导入两端 slug 都存在于新 KB 的关系

Step 4: 重建索引页
        └── 更新 index/home 的内容，反映新的目录结构
```

**为什么先 v2 后参考库？**
- v2 的摘要页和索引页是定制的，要保留
- 参考库的 pages 导入时不会覆盖 v2 已有的页面（因为零冲突）
- relations 最后导入，确保两端页面都已经存在

### 3.5 索引页重建策略

合并后顶层目录从 3 个变成 9 个，索引页内容需要完全重建。重建规则：

1. **每类目录至多显示 10 个条目**，超过用 "..." 表示
   - 理由：有些目录（如"保险"下的子概念）条目非常多，全部列出来会让索引页很长
   - 操作：取前 10 个，后面加 `...（共 N 个）` 的提示

2. **11 篇摘要全部完整列出（不截断）**
   - 理由：摘要数量少（只有 11 篇），是用户最常访问的入口，应该全部可见

3. **已删除的目录要从索引中同步移除**
   - 理由：参考库里有些目录（如公司法）和本场景无关，合并时会跳过或删除
   - 操作：索引页的章节要和实际文件夹一致，不要保留已删除目录的章节

4. **索引页结构建议：**
   ```
   # 知识库索引
   
   ## 📑 摘要（11篇）
   - [摘要1](...)
   - [摘要2](...)
   ...
   
   ## 📚 法规（11篇）
   - [法规1](...)
   ...
   
   ## 🏷️ 主题分类
   ### 保险
   - xxx
   - yyy
   - ...（共 N 个）
   
   ### 保险监管
   - ...
   
   ## 📋 条款
   - ...
   
   ## 🧩 业务对象
   - ...
   ```

## 四、文档与切片复制

### 4.1 文档 Tab 与 Wiki Tab 是两套独立体系

- **Wiki 体系**：`wiki_pages` + `wiki_folders` + `wiki_page_relations` → 服务于"知识/摘要/索引" Tab
- **文档体系**：`knowledges` + `chunks` → 服务于"文档" Tab

两者完全独立，互不冲突。一个知识库可以同时有 wiki 页面和文档，也可以只有其中一种。

**关键区别：**

| 维度 | Wiki 体系 | 文档体系 |
|------|----------|---------|
| 数据表 | wiki_pages, wiki_folders, wiki_page_relations | knowledges, chunks |
| 前端Tab | 知识 / 摘要 / 索引 | 文档 |
| 内容结构 | 页面 + 目录树 + 关系图谱 | 文档 + 切片（用于RAG检索） |
| 摘要字段 | wiki_pages.summary（一句话） | knowledges.summary（文档摘要） |

### 4.2 复制文档的步骤

从参考库复制文档（knowledges + chunks）到新 KB，步骤如下：

```
Step 1: 复制 knowledges 记录
        ├── 从参考库 SELECT 所有 knowledges
        ├── 全部 UUID 重新生成（id 字段）
        ├── knowledge_base_id 改为新 KB 的 ID
        └── 插入到新 KB

Step 2: 建立 old_knowledge_id → new_knowledge_id 映射
        └── 按标题匹配（title 相同的视为同一个文档）

Step 3: 复制 chunks
        ├── 从参考库 SELECT 所有 chunks（按 knowledge_id 过滤）
        ├── chunk 的 id 全部用 gen_random_uuid() 重新生成
        ├── knowledge_id 映射到新的 ID
        ├── knowledge_base_id 改为新 KB 的 ID
        └── seq_id 全局重新生成（见下一节）
```

### 4.3 chunks 的 seq_id 全局唯一问题

**坑点：** `chunks.seq_id` 有一个全局唯一索引 `idx_chunks_seq_id`，是跨所有知识库的全局唯一，不是每个 KB 独立。

**❌ 错误做法：** 直接 INSERT 复制 chunks，保留原来的 seq_id

**后果：** 报唯一索引冲突错误，因为 seq_id 已经被参考库的 chunk 占用了。

**✅ 正确做法：** 用 `max_seq + ROW_NUMBER()` 重新生成：

```sql
-- 先获取当前最大 seq_id
SELECT MAX(seq_id) FROM chunks;  -- 假设得到 max_seq = 12345

-- 插入新 chunks 时，seq_id 重新编号
INSERT INTO chunks (id, tenant_id, knowledge_base_id, knowledge_id, seq_id, content, ...)
SELECT
    gen_random_uuid(),
    10000,
    'kb-regscene-demo-003',
    new_knowledge_map.new_id,
    max_seq + ROW_NUMBER() OVER (ORDER BY c.seq_id),  -- 全局重新编号
    c.content,
    ...
FROM chunks c
JOIN new_knowledge_map ON c.knowledge_id = new_knowledge_map.old_id
WHERE c.knowledge_base_id = '参考库ID';
```

**Python 实现要点：**
1. 先查 `SELECT MAX(seq_id) FROM chunks` 得到当前最大值
2. 遍历 chunks 列表时，每条的 seq_id = max_seq + offset + 1（offset 从 0 开始递增）
3. chunk.id 全部用 `uuid.uuid4()` 新生成，绝对不能复用

## 五、⚠️ 关键踩坑点（务必注意）

### 5.1 depth 字段必须等于 category_path 数组长度

**❌ 错误理解：** `depth = folder.depth + 1`（把文件夹深度+1当页面深度）

**✅ 正确规则：** `depth = jsonb_array_length(category_path)`

验证方式：看参考库（`82b8c8c8-519f-4a2e-ac1d-09f2dd8a17d9`）的数据：
- `category_path = []` → `depth = 0`
- `category_path = ['保险']` → `depth = 1`
- `category_path = ['保险', '互联网保险']` → `depth = 2`

**为什么重要：** 前端树视图加载文件夹下的页面时，会传 `category_depth = categoryPath.length`，后端用 `depth = category_depth` 过滤。如果depth多算了1，页面永远查不出来，树视图展开就是空的。

**修复SQL：**
```sql
UPDATE wiki_pages
SET depth = jsonb_array_length(category_path)
WHERE knowledge_base_id = 'xxx'
  AND category_path != '[]'::jsonb;
```

### 5.2 category_path 决定页面在树视图中的位置

页面不会因为有 `folder_id` 就自动出现在文件夹下——前端树视图是按 `category_path` 分组的，不是按 `folder_id` 关联的。

导入时必须同时设置：
- `folder_id`（数据库关联用）
- `category_path`（前端树视图分组用）
- `depth`（必须 = len(category_path)）
- `wiki_path`（排序用，= folder.path + '/' + slug）

**批量修复category_path的SQL：**
```sql
UPDATE wiki_pages p
SET category_path = string_to_array(f.path, '/')::jsonb,
    depth = jsonb_array_length(string_to_array(f.path, '/')::jsonb),
    wiki_path = f.path || '/' || p.slug
FROM wiki_folders f
WHERE p.folder_id = f.id
  AND p.knowledge_base_id = 'xxx'
  AND p.folder_id != '';
```

### 5.3 摘要页（summary类型）要放在根目录

- **folder_id = ''**（空字符串，不是NULL）
- **category_path = []**（空数组）
- **depth = 0**

这样"摘要"Tab下才会平铺显示所有摘要页，没有目录树，和参考库"法律法规库"一致。

### 5.4 摘要页 vs 法规详情页是两个不同页面

| 维度 | 摘要页（摘要Tab） | 法规详情页（知识Tab） |
|------|-----------------|---------------------|
| page_type | summary | entity |
| 位置 | 根目录，平铺 | 法规/xxx通知/ 目录下 |
| 内容 | 精简版（基本信息+核心内容+跳转链接） | 详细版（完整章节） |
| slug前缀 | `summary/` | `entity/regulation-` |
| 数量 | 11 | 11 |

不要混为一谈。法规详情页的内容来自参考库的摘要页（详细版），而摘要页的内容是从法规详情页进一步精简提取的。

### 5.5 JSONB 字段在 psycopg2 中不能直接传 dict

**❌ 错误：**
```python
cur.execute("INSERT ... VALUES (%s, %s)", (id, {"key": "value"}))
```

**✅ 正确：**
```python
import json
cur.execute(
    "INSERT ... VALUES (%s, %s::jsonb)",
    (id, json.dumps({"key": "value"}, ensure_ascii=False))
)
```

所有 JSONB 字段（category_path, aliases, source_refs, in_links, out_links, page_metadata）都需要用 `json.dumps()` 转成字符串，再加 `::jsonb` 类型转换。

### 5.6 knowledge_bases 表的 config 字段也是 JSONB

新建知识库时，`config` 字段（字典类型）同样需要 `json.dumps()` + `::jsonb`。

### 5.7 ⭐ 合并前一定要做 slug 冲突分析

**新增（v3踩坑）：** 合并两个知识库之前，必须先检查 slug 是否有冲突。

```sql
-- 检查两个 KB 之间的 slug 冲突
SELECT v2.slug, v2.title AS v2_title, ref.title AS ref_title
FROM wiki_pages v2
JOIN wiki_pages ref ON v2.slug = ref.slug
WHERE v2.knowledge_base_id = 'kb-v2'
  AND ref.knowledge_base_id = 'kb-ref'
  AND v2.deleted_at IS NULL
  AND ref.deleted_at IS NULL;
```

如果返回任何结果，说明有冲突，需要先在其中一个库里重命名 slug，再合并。**零冲突是合并的前提条件。**

### 5.8 ⭐ 索引页内容要和目录同步

**新增（v3踩坑）：** 删除了目录中的文件夹，索引页里也要去掉对应章节。

比如参考库里有"公司法"目录，但法规场景不需要，合并时跳过了这个目录的文件夹和页面。如果索引页还是用参考库的模板生成，就会保留"公司法"章节，但点击进去是空的（因为页面没导入）。

**原则：索引页的每个章节都必须对应实际存在的文件夹和页面。**

### 5.9 ⭐ chunk 复制的两个易错点

**新增（v3踩坑）：** 复制 chunks 时有两个地方容易错：

1. **seq_id 全局唯一**（不是每个KB独立），直接复制会报唯一索引冲突
   - 必须用 `max_seq + ROW_NUMBER()` 重新生成 seq_id

2. **chunk id 不能复用**，必须用新 UUID，否则主键冲突
   - 全部用 `gen_random_uuid()` 或 `uuid.uuid4()` 重新生成

**检查方式：** 复制完之后跑一下校验 SQL（见第七章），确认数量和唯一性都没问题。

## 六、内容生成最佳实践

### 6.1 从参考库提取精简摘要用 Agent，不用正则

**问题：** 11篇参考文档的摘要格式不统一：
- 有的有 `## 文件基本信息` 章节
- 有的标题下面直接是 `**字段**：值`
- 有的叫 `## 文件概况`
- 字段名也各不相同（发文字号/文号/文编号，施行日期/实施日期/执行日期...）

用正则提取会漏掉很多，导致基本信息为空。

**方案：** 用11个子agent分别处理每篇文档，LLM能灵活识别不同格式的基本信息字段。

**Agent Prompt 模板：**
```
请读取 /tmp/ref_docs/docXX.json 文件，这是一篇保险监管法规的详细摘要页内容（Markdown格式）。

你的任务：从这篇详细摘要中，提取出一个精简版摘要，结构如下：

# <法规名称（去掉.pdf - Summary后缀）>

## 文件基本信息
- **发布机构**：xxx
- **发布日期**：xxx
- **文号**：xxx
- **施行日期**：xxx
- **效力状态**：xxx
（根据原文实际有的内容提取，没有的字段就不列，但至少要有3-6项基本信息）

## 核心内容
- <核心要点1>
- <核心要点2>
- <核心要点3>
（提取3-5个最核心的要点，每点一句话）

---
📄 完整内容及条款详情请查看：[[entity/regulation-<slug后缀>|法规详情页]]

要求：
1. 保留 Markdown 格式
2. 去掉原文中的 wiki 链接（[[xxx|yyy]] 只保留显示文本 yyy）
3. 文件基本信息要从原文中准确提取，字段名可能不同，要灵活识别
4. 核心内容要是原文真正的核心要点，不是目录标题
```

### 6.2 条款和业务对象从PDF原文提取

每篇PDF文档用一个子agent提取：
- 条款：提取原文中的具体条款（编号+标题+内容）
- 业务对象：提取文中出现的核心业务概念（定义、属性）

输出格式统一为 JSON，便于批量入库。

### 6.3 Slug 命名规范

| 页面类型 | slug前缀 | 示例 |
|---------|---------|------|
| 法规详情页 | `entity/regulation-` | `entity/regulation-个税优惠健康险通知` |
| 条款页 | `entity/clause-` | `entity/clause-doc01-c-001` |
| 业务对象页 | `entity/` | `entity-预定附加费用率` |
| 精简摘要页 | `summary/` | `summary/个税优惠健康险通知` |
| 索引页 | `index/` | `index/home` |
| 主题概念页（参考库） | `concept/` 或 `entity/` | `concept/人寿保险` |

**注意：** 所有slug在同一个知识库中必须唯一。条款和业务对象都用 `entity/` 前缀时，要通过子前缀（`clause-`、`regulation-`）避免冲突。参考库导入的 concept/entity 前缀不会和 v2 的冲突（见第三章分析）。

## 八、常用 SQL 验证脚本

### 8.1 检查页面数量和类型分布
```sql
SELECT page_type, count(*) 
FROM wiki_pages 
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
GROUP BY page_type ORDER BY page_type;
```

### 8.2 检查 depth 是否正确
```sql
SELECT category_path, depth, count(*)
FROM wiki_pages
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
GROUP BY category_path, depth
ORDER BY category_path;
-- 验证：depth = jsonb_array_length(category_path)
```

### 8.3 检查文件夹结构
```sql
SELECT path, depth, name
FROM wiki_folders
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
ORDER BY path;
```

### 8.4 检查关系数量
```sql
SELECT relation_type, count(*)
FROM wiki_page_relations
WHERE source_slug IN (SELECT slug FROM wiki_pages WHERE knowledge_base_id = 'xxx')
   OR target_slug IN (SELECT slug FROM wiki_pages WHERE knowledge_base_id = 'xxx')
GROUP BY relation_type;
```

### 8.5 模拟前端树查询（验证页面能被查到）
```sql
-- 查条款目录下的页面（前端传 category_depth=1）
SELECT slug, title, category_path, depth
FROM wiki_pages
WHERE knowledge_base_id = 'xxx'
  AND deleted_at IS NULL
  AND page_type = 'entity'
  AND category_path::jsonb = '["条款"]'::jsonb
  AND depth = 1
ORDER BY wiki_path
LIMIT 20;
-- 如果返回0条，说明depth或category_path有问题
```

### 8.6 检查 slug 唯一性 【v3新增】
```sql
-- 检查单个 KB 内是否有重复 slug
SELECT slug, count(*)
FROM wiki_pages
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
GROUP BY slug
HAVING count(*) > 1;
-- 应该返回0行，返回任何行都说明有重复slug

-- 检查两个 KB 之间的 slug 冲突（合并前用）
SELECT v2.slug, v2.title AS v2_title, ref.title AS ref_title
FROM wiki_pages v2
JOIN wiki_pages ref ON v2.slug = ref.slug
WHERE v2.knowledge_base_id = 'kb-v2'
  AND ref.knowledge_base_id = 'kb-ref'
  AND v2.deleted_at IS NULL
  AND ref.deleted_at IS NULL;
```

### 8.7 检查死链（wiki链接指向不存在的slug） 【v3新增】
```sql
-- 检查某个KB中，页面content里的wiki链接指向了不存在的slug
WITH all_slugs AS (
    SELECT slug FROM wiki_pages WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
),
page_links AS (
    SELECT 
        slug AS source_slug,
        (regexp_matches(content, '\[\[([^\]|]+)(\|[^\]]+)?\]\]', 'g'))[1] AS target_slug
    FROM wiki_pages
    WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
      AND content LIKE '%[[%'
)
SELECT DISTINCT pl.source_slug, pl.target_slug
FROM page_links pl
LEFT JOIN all_slugs s ON pl.target_slug = s.slug
WHERE s.slug IS NULL
ORDER BY pl.source_slug, pl.target_slug;
-- 返回的每一行都是一个死链（源页面链接到了不存在的目标slug）
```

### 8.8 检查 knowledges 和 chunks 数量 【v3新增】
```sql
-- 检查文档数量
SELECT count(*) AS knowledge_count
FROM knowledges
WHERE knowledge_base_id = 'xxx';

-- 检查切片数量
SELECT count(*) AS chunk_count
FROM chunks
WHERE knowledge_base_id = 'xxx';

-- 检查每个文档的切片数量
SELECT k.title, count(c.id) AS chunk_count
FROM knowledges k
LEFT JOIN chunks c ON k.id = c.knowledge_id
WHERE k.knowledge_base_id = 'xxx'
GROUP BY k.id, k.title
ORDER BY chunk_count DESC;

-- 检查 chunks seq_id 是否有重复（全局唯一索引）
SELECT seq_id, count(*)
FROM chunks
GROUP BY seq_id
HAVING count(*) > 1;
-- 应该返回0行
```

## 十、下次新建知识库的快速步骤（v3版）

1. **定一个新的KB ID**，比如 `kb-regscene-v5`

2. **新建知识库记录**

   - 统计死链数量

   - folders → pages → relations 的顺序
   - KB ID 全部替换为新 ID

5. **合并参考库主题目录**
   - 导入参考库 folders（跳过不需要的目录）

   - knowledges：UUID 重新生成，KB ID 替换
   - 建立 old→new knowledge_id 映射（按标题）

   - 11 篇摘要完整列出
   - 已删除目录从索引中移除

8. **数据校验**
   - 跑一遍第八章的所有校验 SQL
   - 重点关注：slug 唯一、depth 正确、无死链、chunks seq_id 无重复

9. **前端验证**
   - 知识Tab各目录展开正常
   - 摘要Tab正常
   - 文档Tab正常
   - wiki链接跳转正常
   - 关系图谱正常
