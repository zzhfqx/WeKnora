## 一、总体架构回顾

### 1.1 三层结构（自底向上）

```
一级目录（3个，顶层文件夹）
  ├── 法规          （文件夹，depth=1）
  │     └── 每篇法规/  （子文件夹，depth=2）
  │           └── 法规详情页  （entity页面，depth=2）
  ├── 条款          （文件夹，depth=1）
  │     └── 条款1..n  （entity页面，depth=1）
  └── 业务对象       （文件夹，depth=1）
        └── BO1..n   （entity页面，depth=1）
```

### 1.2 页面类型与 Tab 对应关系

| 前端Tab | 包含的 page_type | 本项目中的用途 |
|---------|-----------------|--------------|
| 知识     | entity + concept + synthesis + comparison | 法规详情页、条款页、业务对象页（全用 entity） |
| 摘要     | summary | 精简摘要页（11篇，平铺展示，无目录树） |
| 索引     | index | 知识库首页 |

**重要：** 条款和业务对象都用 `entity` 类型，统一在"知识"Tab下展示。不要用 `concept`，避免分散到不同Tab。

## 三、⚠️ 关键踩坑点（务必注意）

### 3.1 depth 字段必须等于 category_path 数组长度

**❌ 错误理解：** `depth = folder.depth + 1`（把文件夹深度+1当页面深度）

**✅ 正确规则：** `depth = jsonb_array_length(category_path)`

验证方式：看参考库（`82b8c8c8-519f-4a2e-ac1d-09f2dd8a17d9`）的数据：
- `category_path = []` → `depth = 0`
- `category_path = ['保险']` → `depth = 1`
- `category_path = ['保险', '互联网保险']` → `depth = 2`

**为什么重要：** 前端树视图加载文件夹下的页面时，会传 `category_depth = categoryPath.length`，后端用 `depth = category_depth` 过滤。如果depth多算了1，页面永远查不出来，树视图展开就是空的。

**修复SQL：**
```sql
UPDATE wiki_pages
SET depth = jsonb_array_length(category_path)
WHERE knowledge_base_id = 'xxx'
  AND category_path != '[]'::jsonb;
```

### 3.2 category_path 决定页面在树视图中的位置

页面不会因为有 `folder_id` 就自动出现在文件夹下——前端树视图是按 `category_path` 分组的，不是按 `folder_id` 关联的。

导入时必须同时设置：
- `folder_id`（数据库关联用）
- `category_path`（前端树视图分组用）
- `depth`（必须 = len(category_path)）
- `wiki_path`（排序用，= folder.path + '/' + slug）

**批量修复category_path的SQL：**
```sql
UPDATE wiki_pages p
SET category_path = string_to_array(f.path, '/')::jsonb,
    depth = jsonb_array_length(string_to_array(f.path, '/')::jsonb),
    wiki_path = f.path || '/' || p.slug
FROM wiki_folders f
WHERE p.folder_id = f.id
  AND p.knowledge_base_id = 'xxx'
  AND p.folder_id != '';
```

### 3.3 摘要页（summary类型）要放在根目录

- **folder_id = ''**（空字符串，不是NULL）
- **category_path = []**（空数组）
- **depth = 0**

这样"摘要"Tab下才会平铺显示所有摘要页，没有目录树，和参考库"法律法规库"一致。

### 3.4 摘要页 vs 法规详情页是两个不同页面

| 维度 | 摘要页（摘要Tab） | 法规详情页（知识Tab） |
|------|-----------------|---------------------|
| page_type | summary | entity |
| 位置 | 根目录，平铺 | 法规/xxx通知/ 目录下 |
| 内容 | 精简版（基本信息+核心内容+跳转链接） | 详细版（完整章节） |
| slug前缀 | `summary/` | `entity/regulation-` |
| 数量 | 11 | 11 |

不要混为一谈。法规详情页的内容来自参考库的摘要页（详细版），而摘要页的内容是从法规详情页进一步精简提取的。

### 3.5 JSONB 字段在 psycopg2 中不能直接传 dict

**❌ 错误：**
```python
cur.execute("INSERT ... VALUES (%s, %s)", (id, {"key": "value"}))
```

**✅ 正确：**
```python
import json
cur.execute(
    "INSERT ... VALUES (%s, %s::jsonb)",
    (id, json.dumps({"key": "value"}, ensure_ascii=False))
)
```

所有 JSONB 字段（category_path, aliases, source_refs, in_links, out_links, page_metadata）都需要用 `json.dumps()` 转成字符串，再加 `::jsonb` 类型转换。

### 3.6 knowledge_bases 表的 config 字段也是 JSONB

新建知识库时，`config` 字段（字典类型）同样需要 `json.dumps()` + `::jsonb`。

## 四、内容生成最佳实践

### 4.1 从参考库提取精简摘要用 Agent，不用正则

**问题：** 11篇参考文档的摘要格式不统一：
- 有的有 `## 文件基本信息` 章节
- 有的标题下面直接是 `**字段**：值`
- 有的叫 `## 文件概况`
- 字段名也各不相同（发文字号/文号/文编号，施行日期/实施日期/执行日期...）

用正则提取会漏掉很多，导致基本信息为空。

**方案：** 用11个子agent分别处理每篇文档，LLM能灵活识别不同格式的基本信息字段。

**Agent Prompt 模板：**
```
请读取 /tmp/ref_docs/docXX.json 文件，这是一篇保险监管法规的详细摘要页内容（Markdown格式）。

你的任务：从这篇详细摘要中，提取出一个精简版摘要，结构如下：

# <法规名称（去掉.pdf - Summary后缀）>

## 文件基本信息
- **发布机构**：xxx
- **发布日期**：xxx
- **文号**：xxx
- **施行日期**：xxx
- **效力状态**：xxx
（根据原文实际有的内容提取，没有的字段就不列，但至少要有3-6项基本信息）

## 核心内容
- <核心要点1>
- <核心要点2>
- <核心要点3>
（提取3-5个最核心的要点，每点一句话）

---
📄 完整内容及条款详情请查看：[[entity/regulation-<slug后缀>|法规详情页]]

要求：
1. 保留 Markdown 格式
2. 去掉原文中的 wiki 链接（[[xxx|yyy]] 只保留显示文本 yyy）
3. 文件基本信息要从原文中准确提取，字段名可能不同，要灵活识别
4. 核心内容要是原文真正的核心要点，不是目录标题
```

### 4.2 条款和业务对象从PDF原文提取

每篇PDF文档用一个子agent提取：
- 条款：提取原文中的具体条款（编号+标题+内容）
- 业务对象：提取文中出现的核心业务概念（定义、属性）

输出格式统一为 JSON，便于批量入库。

### 4.3 Slug 命名规范

| 页面类型 | slug前缀 | 示例 |
|---------|---------|------|
| 法规详情页 | `entity/regulation-` | `entity/regulation-个税优惠健康险通知` |
| 条款页 | `entity/clause-` | `entity/clause-doc01-c-001` |
| 业务对象页 | `entity/` | `entity-预定附加费用率` |
| 精简摘要页 | `summary/` | `summary/个税优惠健康险通知` |
| 索引页 | `index/` | `index/home` |

**注意：** 所有slug在同一个知识库中必须唯一。条款和业务对象都用 `entity/` 前缀时，要通过子前缀（`clause-`、`regulation-`）避免冲突。

## 六、常用 SQL 验证脚本

### 6.1 检查页面数量和类型分布
```sql
SELECT page_type, count(*) 
FROM wiki_pages 
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
GROUP BY page_type ORDER BY page_type;
```

### 6.2 检查 depth 是否正确
```sql
SELECT category_path, depth, count(*)
FROM wiki_pages
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
GROUP BY category_path, depth
ORDER BY category_path;
-- 验证：depth = jsonb_array_length(category_path)
```

### 6.3 检查文件夹结构
```sql
SELECT path, depth, name
FROM wiki_folders
WHERE knowledge_base_id = 'xxx' AND deleted_at IS NULL
ORDER BY path;
```

### 6.4 检查关系数量
```sql
SELECT relation_type, count(*)
FROM wiki_page_relations
WHERE source_slug IN (SELECT slug FROM wiki_pages WHERE knowledge_base_id = 'xxx')
   OR target_slug IN (SELECT slug FROM wiki_pages WHERE knowledge_base_id = 'xxx')
GROUP BY relation_type;
```

### 6.5 模拟前端树查询（验证页面能被查到）
```sql
-- 查条款目录下的页面（前端传 category_depth=1）
SELECT slug, title, category_path, depth
FROM wiki_pages
WHERE knowledge_base_id = 'xxx'
  AND deleted_at IS NULL
  AND page_type = 'entity'
  AND category_path::jsonb = '["条款"]'::jsonb
  AND depth = 1
ORDER BY wiki_path
LIMIT 20;
-- 如果返回0条，说明depth或category_path有问题
```

## 八、下次新建知识库的快速步骤

1. **定一个新的KB ID**，比如 `kb-regscene-v3`
2. **复制** `import_regscene_v4.py` 脚本为 `import_regscene_v5.py`
3. **修改** KB ID、源数据路径
4. **特别注意** 下面这些容易错的地方：
   - JSONB 字段都用 `json.dumps()` + `::jsonb`
   - `depth = len(category_path)`（不要+1）
   - 摘要页放根目录（folder_id=''，category_path=[]，depth=0）
   - 所有 slug 唯一
5. **运行导入脚本**
6. **跑一遍第六节的校验SQL**
7. **前端验证**

如果树视图展开看不到页面，99%的概率是 depth 或 category_path 不对，直接查 6.2 和 6.5 的SQL。
