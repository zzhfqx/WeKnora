### 2.3 Go 学习笔记：Python 开发者视角的核心语法差异

> 持续更新，记录从 Python 转 Go 过程中遇到的语法差异和理解要点，供团队快速查阅。

#### 2.3.1 import 导包

Go 的 `import` 和 Python 的 `import` 本质一样（都是引入外部模块），但规则和写法差异很大：

| 特性 | Python | Go |
|------|--------|-----|
| 语法 | 一行一个 `import` | 括号包成一组 `import (...)` |
| 导入方式 | `import os` 或 `from x import y` | 只能导入整个包，没有 `from` |
| 调用方式 | `模块名.xxx` | **包名（目录名）.xxx**，不是路径 |
| 别名 | `import numpy as np` | `import np "xxx/xxx"`（写在路径前） |
| 无用导入 | 不报错，只是浪费 | **编译不通过**，强制清理 |
| 标准库识别 | 不直观（需记忆） | 路径短的就是标准库，域名开头的是第三方 |
| 相对导入 | `from .utils import x` | 不支持，必须写完整模块路径 |

**示例对照：**

```python
# Python
import os
from pathlib import Path

path = Path(os.getenv("HOME"))
```

```go
// Go
import (
    "os"
    "path"
)

func main() {
    home := os.Getenv("HOME")       // 用包名 os 调用
    fullPath := path.Join(home, "go")  // 用包名 path 调用
}
```

**项目内包的导入路径：**

Go 项目内的包导入要写完整的「模块路径 + 目录路径」，但调用时只用最后一段目录名（包名）：

```go
import (
    // 导入路径很长...
    "github.com/Tencent/WeKnora/internal/models/chat"
    "github.com/Tencent/WeKnora/internal/types"
)

func main() {
    // 调用时只用包名 chat 和 types，很短
    config := &chat.ChatConfig{
        Source: types.ModelSourceRemote,
    }
}
```

**要点提醒：**
1. 导入了就必须用，否则编译报错——这是 Go 强制代码整洁的方式
2. 调用用「包名」不是「import 路径」，包名通常等于目录名
3. 标准库路径都是短名字（`fmt`、`os`、`context`），第三方都是域名开头

#### 2.3.2 变量声明与结构体初始化（`:=`、`&`、`{}`）

Go 的变量声明和对象初始化和 Python 差异很大，一行代码里可能同时出现 `:=`、`&`、`{}` 三个新符号：

```go
config := &chat.ChatConfig{
    Source:    types.ModelSourceRemote,
    BaseURL:   baseURL,
    APIKey:    apiKey,
    ModelName: modelName,
    ModelID:   "demo-model",
    Provider:  "openai",
}
```

**对应 Python：**
```python
config = ChatConfig(
    source=ModelSource.REMOTE,
    base_url=base_url,
    api_key=api_key,
    model_name=model_name,
    model_id="demo-model",
    provider="openai",
)
```

##### `:=` — 短变量声明

| 特性 | Python | Go |
|------|--------|-----|
| 声明变量 | `x = 123`（直接赋值） | `x := 123`（声明+推断类型+赋值） |
| 类型 | 动态类型，运行时确定 | 编译期推断，类型确定后不能变 |
| 作用域 | 函数内随便写 | 只能在函数内部用，全局变量用 `var` |

> Go 也有完整写法 `var x int = 123`，但 `:=` 用得最多，因为不用写类型。

##### `&` — 取地址（指针）

Python 没有这个概念，Python 的对象默认就是引用传递。Go 里要显式区分：

| 类型 | 写法 | 含义 | 类比 Python |
|------|------|------|------------|
| 值类型 | `chat.ChatConfig` | 存的是完整数据，传参会拷贝一份 | 类比 Python 的 int/float（传值） |
| 指针类型 | `*chat.ChatConfig` | 存的是内存地址，传参共享同一份 | 类比 Python 的 dict/list/对象（传引用） |

**什么时候用 `&`？**
- 结构体比较大，不想拷贝
- 函数需要修改原始值（传值的话改的是副本）
- 需要表示"空"的状态（指针可以是 nil，值类型不行）

> **Python 开发者速记：** 看到 `&xxx{...}` 就当成 Python 的对象引用，效果差不多，只是 Go 要显式写出来。

##### `{}` — 结构体字面量

Go 的结构体初始化用花括号 `{}`，不是圆括号 `()`：

```go
// Go：结构体字面量，字段名: 值
person := Person{
    Name: "张三",
    Age:  25,
}
```

```python
# Python：调用构造函数
person = Person(name="张三", age=25)
```

**为什么 Go 用 `{}` 而不是 `()`？**
- Go **没有构造函数**（语言层面不强制）
- `{}` 是直接填字段，不是在"调用函数"
- 如果需要构造逻辑（校验、默认值），自己写 `NewPerson()` 函数——这是 Go 的惯例

##### 指针符号对比：`&` vs `*`

别搞反了：

| 符号 | 作用 | 例子 |
|------|------|------|
| `&` | **取地址**（值 → 指针） | `&config` 拿到 config 的指针 |
| `*` | **解引用**（指针 → 值） | `*ptr` 通过指针拿到原值 |

在类型声明里 `*Type` 表示「指向 Type 的指针」：
```go
var ptr *chat.ChatConfig  // ptr 是指针类型，可以为 nil
```

> 日常开发大部分时候只需要 `&`（取地址传参），`*` 用得比较少。

#### 2.3.3 输出与格式化（`fmt.Println` / `fmt.Printf`）

Go 用标准库 `fmt` 包做输出，最常用的两个函数：

| Go | Python | 说明 |
|----|--------|------|
| `fmt.Println(x)` | `print(x)` | 打印 + 自动换行 |
| `fmt.Printf("...%s...", x)` | `print(f"...{x}...")` | 格式化打印（**不自动换行**，要手动加 `\n`） |
| `fmt.Print(x)` | `print(x, end="")` | 打印不换行 |

**常用占位符：**

| 占位符 | 含义 | Python 对应 |
|--------|------|------------|
| `%s` | 字符串 | `%s` / f-string `{}` |
| `%d` | 整数 | `%d` |
| `%f` | 浮点数 | `%f` |
| `%v` | 任意值（默认格式） | f-string `{}` |
| `%+v` | 结构体详细打印（显示字段名） | `pprint.pprint()` |
| `%%` | 字面量 `%` | `%%` |

**示例：**

```go
// 简单输出
fmt.Println("启动成功")                           // 启动成功\n

// 格式化输出（注意手动加 \n）
fmt.Printf("baseURL=%s, model=%s\n", url, name)   // baseURL=xxx, model=xxx\n

// 调试打印结构体
fmt.Printf("配置：%+v\n", config)                  // 字段名+值全打出来
```

> Go 的格式化语法继承自 C 语言 `printf`，和 Python 的 `%` 格式化用法基本一致。

#### 2.3.4 结构体定义（`type Xxx struct`）

Go 用结构体（struct）定义数据结构，相当于 Python 的类（只存数据的那种）。

**定义方式：**

```go
type ChatConfig struct {
    Source    types.ModelSource
    BaseURL   string
    ModelName string
    APIKey    string
    ModelID   string
    Provider  string
}
```

**对应 Python：**

```python
@dataclass
class ChatConfig:
    source: ModelSource
    base_url: str
    model_name: str
    api_key: str
    model_id: str
    provider: str
```

| Go 语法 | Python 对应 | 说明 |
|---------|------------|------|
| `type ChatConfig struct` | `class ChatConfig:` | 定义一个类型/类 |
| 字段名 + 类型（如 `BaseURL string`） | 属性名 + 类型注解（如 `base_url: str`） | 定义有哪些属性 |
| `ChatConfig{...}` 结构体字面量 | `ChatConfig(...)` 实例化 | 创建实例 |
| `&ChatConfig{...}` | （Python 默认就是引用） | 创建实例并取指针 |

**使用方式：**

```go
// 1. 声明变量
var config chat.ChatConfig

// 2. 创建实例（常用）
config := &chat.ChatConfig{
    BaseURL:   "https://api.example.com",
    ModelName: "gpt-4",
}

// 3. 作为函数参数
func NewChat(config *ChatConfig) (Chat, error) {
    // config 是指针类型 *ChatConfig
}
```

**值类型 vs 指针类型：**

| 写法 | 类型 | 含义 |
|------|------|------|
| `chat.ChatConfig` | 值类型 | 存完整数据，传参会拷贝 |
| `*chat.ChatConfig` | 指针类型 | 存内存地址，传参共享同一份 |
| `&chat.ChatConfig{...}` | 取地址表达式 | 创建结构体并拿到指针 |

> Go 没有类（class）的概念，结构体 + 方法 = Go 的"类"。结构体只负责存数据，方法（函数）是单独挂上去的。

## 三、Go 架构的优势

### 3.1 性能与并发

- **天生高并发**：goroutine 比 Python 的 asyncio 线程轻量得多，处理大量文档解析、向量索引等 I/O 密集型任务优势明显
- **内存占用低**：编译型语言，无 GIL，同样的并发量下内存占用远低于 Python
- **启动快**：后端服务秒级启动，Python 的 FastAPI/Django 冷启动要慢很多

### 3.2 工程质量

- **强类型 + 编译期检查**：重构和大改动时安全感高，编译器能抓出绝大多数低级错误
- **代码风格高度统一**：Go 有官方的 `gofmt`，团队代码风格一致，读别人的代码不费劲
- **依赖管理清晰**：`go.mod` + `go.sum`，没有 Python 的 pip/conda/poetry 环境混乱问题
- **部署简单**：编译成单个二进制文件，扔哪都能跑，不需要装 Python 环境

### 3.3 项目本身的工程质量

- 分层清晰（handler → service → repository），职责明确
- Wiki 生成流程采用 Map-Reduce 异步管道架构，设计合理
- prompt 管理有统一入口（`generateWithTemplate`），不是到处散着调 LLM
- 有完善的 migration 体系和配置管理

## 四、主要风险与挑战

### 4.1 人才与学习成本

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 团队不熟悉 Go | 初期开发速度慢 | 先从改小功能入手，逐步积累经验；关键功能先做原型验证 |
| 招人难 | Go 工程师比 Python 少 | 内部培养为主，利用现有后端基础 |
| 调试效率低 | 排查问题耗时长 | 建立常见问题排查手册（本文档持续更新） |

### 4.2 技术债务风险

- **改不动就绕着走**：因为不熟悉 Go，遇到复杂逻辑可能用"凑合用"的方式实现，积累技术债
- **最佳实践缺失**：Go 有自己的惯用写法（错误处理、接口设计、并发模式），用 Python 思维写 Go 会写出"四不像"代码

### 4.3 业务逻辑复杂度

- Wiki 生成流程涉及 Map-Reduce、异步任务队列、LLM 调用链、向量检索等，本身就复杂
- 叠加 Go 语言的不熟悉，排查问题时是"业务复杂度 × 语言不熟悉"的双重难度

## 五、可行性结论

### 5.1 总体判断：✅ 可行，但需要过渡期

**维护现有功能 + 做中小改动：完全可行。**
- 大部分需求是改配置、改 prompt、加小功能
- 这些改动 Go 和 Python 的差异不大，学会读代码就能改
- 强类型反而让修改更安全，不容易改出隐藏 bug

**大规模重构 / 核心模块重写：需要谨慎。**
- Wiki ingest、混合检索等核心模块逻辑复杂
- 不熟悉 Go 的并发模式（goroutine + channel + context）容易出问题
- 建议先充分理解现有代码，小步迭代，不做大手术

### 5.2 建议的推进路径

**第一阶段：适应期（1-2 周）**
- [x] 跑通开发环境（已完成）
- [x] 理解项目结构（进行中）
- [ ] 能独立修改 prompt、配置、简单接口

**第二阶段：熟练期（1-2 个月）**
- [ ] 能独立完成中等复杂度的功能开发
- [ ] 理解 Wiki ingest 的完整流程
- [ ] 熟悉 Go 的并发和错误处理模式

**第三阶段：深度参与（3 个月+）**
- [ ] 能做核心模块的优化和重构
- [ ] 建立团队自己的 Go 编码规范

### 5.3 关键成功因素

1. **文档积累**：把踩过的坑、排查过程、学到的经验持续记录下来（本文档就是起点）
2. **小步迭代**：先改小功能建立信心，逐步深入核心模块
3. **善用工具**：`gofmt`、`go vet`、IDE 的跳转和重构功能能省很多事
4. **不急着"优化"**：先保证能跑通、改对，性能优化放到理解透彻之后

## 六、对比：如果换成 Python 架构呢？

作为参照，评估一下"把核心逻辑迁回 Python"的成本：

| 维度 | 维持 Go 架构 | 迁回 Python |
|------|-------------|------------|
| 短期开发速度 | 慢（学习期） | 快 |
| 长期维护成本 | 低（编译检查 + 统一风格） | 中（类型松散 + 依赖管理） |
| 性能 | 好 | 差（GIL + 异步复杂度） |
| 迁移成本 | 0 | 极高（核心模块全部重写，至少 2-3 个月） |
| 风险 | 学习曲线 | 迁移期 bug 多、功能不一致 |

**结论：不建议迁移。** 迁移成本远高于学习成本，而且 Go 在并发和性能上的优势对这个项目（大量文档处理、向量检索、异步任务）很重要。
