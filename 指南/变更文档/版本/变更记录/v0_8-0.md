## 一、Wiki 本体改造（核心改动）

### 1.1 Wiki 提示词全面中文化 + 两层本体架构

**文件**：`internal/agent/prompts_wiki.go`

**改动类型**：大幅修改（约 848 行）

**改动内容**：

原版所有 Wiki 提示词为英文，修改版将其全部译为中文，并引入**两层本体（L1/L2）** 架构思想：

| 层级 | 对应物 | 说明 |
|------|--------|------|
| **L1（第一层本体）** | taxonomy 目录（`folder_path`） | 顶层领域分类，是 L2 实体类的上一层级抽象 |
| **L2（第二层本体）** | 实体类页面（`entity/*`） | 业务本体的父类/分类，类别级而非实例级 |

#### 1.1.1 WikiTaxonomyPlanPrompt（分类目录规划）

**原版**：通用的 Wiki 目录分类，支持 2 级目录，按物品本质分类。

**修改版**：
- 明确 L1/L2 本体定位：实体类页面严格只有**一级目录**（path 数组长度必须为 1），不允许二级子目录，避免视觉上造成三层本体的误解
- L1 按**顶层领域**划分（如"法律"、"保险"、"社会保险"、"金融监管"），命名简洁（2-4 字）
- 概念页面（`concept/*`）不受此限制，可保留多级分类
- 所有说明文字和输出格式从英文改为中文

**关键约束**（L2 实体类）：
- 严格只有一级目录
- 同一 L1 领域下的所有 L2 实体类必须挂在同一个一级目录下
- 不使用"XX相关"、"XX类别"等模糊后缀

#### 1.1.2 WikiSummaryPrompt（文档摘要页生成）

**改动**：
- 全文中文化
- 特别注明：`available_wiki_pages` 中的 `entity/` 类型是**实体类（第二层本体）**，是类别/分类级别的页面，不是具体单个事物
- "Key Takeaways" → "要点总结"

#### 1.1.3 WikiKnowledgeExtractPrompt — 知识抽取提示词（改动最大）

**原版**：提取"实体"（人、组织、产品、地点等**具体实例**）和"概念"。

**修改版**：
- 全量中文化
- 将"实体"重新定义为**实体类 = 第二层本体（业务本体的父类/分类）**
- 增加完整的**本体建模层级说明**：
  - L1 顶层领域分类（最宽泛的领域划分）
  - L2 实体类 / 第二层本体（提取目标，如"保险产品类"、"金融机构类"）
  - L3 业务本体 / 第三层本体（具体业务本体类，如"两全保险"）
  - 实例（实际具体事物，如"小康安心享两全保险"）
- 命名风格统一使用"xx类"后缀
- 新增**四条质量规则**：
  1. **粒度一致性**：所有实体类必须在同一抽象层级上
  2. **避免机构类过度膨胀**：机构相关 L2 控制在 2-3 个以内
  3. **语义不重复**：高度重叠的类别合并保留更宽泛的一个
  4. **顶层领域分类视角**：L2 应能归类到少数 L1 下
- 明确"绝对不要提取具体单个实例"（具体公司名、产品名、人名）
- 输出示例从 `Acme Corp` 改为 `金融机构类`

#### 1.1.4 WikiCandidateSlugPrompt / WikiChunkCitationPrompt

**修改版**：
- 中文化
- 强调实体类是第二层本体，不是具体实例

#### 1.1.5 WikiDeduplicationPrompt — 去重提示词

**修改版**：
- 中文化
- 强调"语义类别"层面的去重（不仅是名称相同，语义高度重叠也要合并）

#### 1.1.6 新增：WikiRelationExtractPrompt — 关系抽取提示词

**全新提示词**，用于抽取两个 Wiki 页面（实体类/概念）之间的结构化语义关系：
- 输入两个页面的完整内容（标题、类型、摘要、正文）
- 输出 JSON 格式的关系：`relation_type`、`relation_label`、`reverse_label`、`description`、`confidence`
- 关系类型示例：`is-a`（子类-父类）、`part-of`、`related-to`、`regulates`、`manages` 等
- 置信度范围 0.0-1.0，低于 0.5 的关系被跳过
- 若无明确关系则返回 `relation_type: "none"`

#### 1.1.7 其他提示词

`WikiPageModifySystemPrompt` / `WikiIndexIntroPrompt` / `WikiIndexIntroUpdatePrompt` 等均做了中文化处理。

**升级时注意**：
- 该文件内容较多，升级时需以修改版为准，整体替换或逐个提示词比对
- 注意原版后续版本是否新增了提示词，需要一并中文化并适配本体架构

#### 1.2.2 关系抽取流程（`generatePageRelations`）

**触发时机**：Wiki 摄入流水线的 finalize 阶段，在 `cleanDeadLinks` 和 `injectCrossLinks` 之后执行。

**触发条件**：`synthesisModelID` 非空（即配置了 Wiki 综合模型）。

**工作流程**：

```
Step 1: 收集候选关系对
  └─ 遍历受影响页面 → 提取 out_links → 生成 (source, target) pair 集合

Step 2: 过滤
  ├─ 排除 index / summary 类型页面（只保留 entity / concept）
  ├─ 排除已归档页面
  └─ 查询已有关系表，跳过已存在的配对（避免重复计算）

Step 3: 调用 LLM 抽取关系
  ├─ 惰性加载页面完整内容（缓存复用）
  ├─ 对每一对页面，让 LLM 判断关系类型、标签、描述、置信度
  └─ 并发处理（errgroup）

Step 4: 批量 upsert 到 wiki_page_relations 表
```

**关键设计**：
- 只处理**还没有关系**的配对，已存在的不重复计算
- 页面内容惰性加载 + 缓存，避免重复读 DB
- 使用 `errgroup` 并发调用 LLM，提高吞吐
- 使用 GORM `Clauses(clause.OnConflict{...})` 做 upsert

**升级时注意**：
- `wikiIngestService` 结构体新增了 `db *gorm.DB` 字段
- `NewWikiIngestService` 构造函数新增了 `db *gorm.DB` 参数
- `container.go` 中需要注入该依赖（dig 自动注入，加参数即可）

#### 1.2.3 关系查询 API

**路由**：`GET /knowledgebase/:kb_id/wiki/relations/*slug`

**返回格式**：
```json
{
  "outgoing": [ /* 当前页作为 source 的关系 */ ],
  "incoming": [ /* 当前页作为 target 的关系 */ ]
}
```

**过滤条件**：只返回 `entity` → `entity` 之间的关系（概念相关的关系不返回），按置信度降序，最多 50 条。

### 2.3 后端 Repository：Neo4j 图谱查询

**文件**：`internal/repository/retriever/neo4j/repository.go`（大幅修改）

**改动类型**：新增图谱可视化相关的查询方法

#### 2.3.1 Bug 修复：节点重复创建问题

**原版问题**：`apoc.merge.node` 使用所有标签 + name + kg 作为匹配键，导致同一知识库下同名实体创建重复节点。

**修改后修复**：
- 节点标签简化为**单个知识库级标签**（`kbLabel = prefix + kbID`），不再使用多标签
- 合并匹配键只用 `name`（同一 KB 下同名实体直接合并）
- `attributes` 和 `chunks` 使用 `apoc.coll.union` 合并去重
- 关系两端的节点也用同样的合并策略，避免创建重名空壳节点
- 关系的 `merge.relationship` 不再传入 attributes 参数（简化）

```go
// 修改前
CALL apoc.merge.node(row.labels, {name: row.name, kg: row.knowledge_id}, row.props, {}) YIELD node

// 修改后
CALL apoc.merge.node(row.labels, {name: row.name},
    {attributes: row.attributes, chunks: row.chunks, kg: row.knowledge_id},
    {}
) YIELD node
SET node.attributes = apoc.coll.union(coalesce(node.attributes, []), coalesce(row.attributes, []))
SET node.chunks = apoc.coll.union(coalesce(node.chunks, []), coalesce(row.chunks, []))
SET node.kg = row.knowledge_id
```

**重要性**：这是一个核心 Bug 修复，升级时必须保留。

### 2.6 前端：Neo4jGraphViewer 组件

**文件**：`frontend/src/views/knowledge/wiki/Neo4jGraphViewer.vue`（**新增**，约 1944 行）

**技术方案**：**纯原生 SVG + 手写力导向布局**，不依赖任何第三方图库（D3.js、vis.js 等）。

#### 2.6.1 三种视图模式

| 模式 | 说明 | 加载方式 |
|-----|------|---------|
| **概览模式 (overview)** | 以度数最高节点为中心的 3 跳子图，默认 400 节点上限 | `loadOverviewGraph()` 先找最高度节点，再加载 ego 子图 |
| **全量模式 (full)** | 按度数 Top 800 节点的全量概览 | `loadFullGraph()` |
| **Ego 模式 (ego)** | 以指定节点为中心的 N 跳邻域子图，所有节点清晰显示 | `loadEgoGraph(centerName, depth)` |

#### 2.6.2 力导向模拟（手写实现）

核心力学参数：
```typescript
const MAX_REPULSION_DIST = 400;    // 斥力范围
const EDGE_TARGET_DIST = 120;      // 目标边长
const SPRING_STRENGTH = 0.006;     // 弹簧强度
const ALPHA_DECAY = 0.995;         // 冷却速率
const VELOCITY_DAMPING = 0.62;     // 速度阻尼
const MAX_VELOCITY = 20;           // 最大速度
```

力模拟包含：
1. **节点斥力 + 碰撞约束**：叶子节点（degree≤1）斥力加成 1.8 倍，防止扎堆
2. **弹簧吸引力**：叶子节点边距增大 60%，弹簧减弱 30%
3. **中心重力**：ego 模式重力减弱，保持圈层结构
4. **速度积分 + 阻尼**：每帧更新位置

#### 2.6.3 节点分层配色（按度数百分比）

| 层级 | 阈值 | 颜色 | 标签 |
|-----|------|------|------|
| 核心节点 | ≥ 95% | `#d54941`（红） | 核心节点 |
| 重要节点 | ≥ 80% | `#e37318`（橙） | 重要节点 |
| 一般节点 | ≥ 55% | `#722ed1`（紫） | 一般节点 |
| 常见节点 | ≥ 30% | `#0594fa`（蓝） | 常见节点 |
| 边缘节点 | < 30% | `#2ba471`（绿） | 边缘节点 |

节点半径：log 缩放，8~24px（与 Wiki 图谱一致）。

#### 2.6.4 空壳节点过滤

自动过滤 `chunk_count=0` 且 `attributes` 为空的节点——这类节点是导入关系时 `apoc.merge.node` 自动创建的占位节点，不是真正提取的实体。

#### 2.6.5 交互功能

- **搜索**：支持模糊匹配（前端即时过滤 + 后端搜索建议）
- **跳数过滤**：1/2/3 跳 N 跳子图视图
- **节点拖拽**：鼠标拖拽节点固定位置
- **画布平移**：空白处拖拽平移
- **滚轮缩放**：0.25x ~ 6x
- **单击节点**：高亮邻居 + 打开详情抽屉 + 自动平移
- **双击节点**：切换为该节点的 N 跳视图
- **悬停节点**：高亮邻居，显示关系标签
- **适应屏幕**：一键 fit-to-view
- **显示全部标签**：切换标签显隐

#### 2.6.6 详情抽屉

点击节点打开右侧抽屉，展示：
- **基本信息**：连接度数、邻居数、关联片段数
- **属性标签**：attributes 数组以 tag 形式展示
- **关系类型分布**：横向进度条展示各关系类型占比
- **Top 邻居列表**：点击可跳转到该邻居的 N 跳视图

#### 2.6.7 边的处理

- 双向边合并为一条线，两端都有箭头
- 单向边目标端有箭头
- 关系类型标签默认隐藏，高亮时显示（带白色背景圆角矩形）
- 概览模式下边淡化（opacity 0.4），ego 模式下清晰显示（opacity 0.9）
