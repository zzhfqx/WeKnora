# WeKnora v0.8.0 修改版 → v0.8.2 选择性升级计划

> **编制日期**：2026-10-12
> **升级前版本**：WeKnora v0.8.0（修改版，分支 pg-fqx）
> **升级后目标**：选择性升级 v0.8.2 中对 Wiki 本体建模有价值的改进
> **策略**：只升级高价值、低风险、不破坏现有逻辑的改进项，不全量升级

## 一、WeKnora 各项能力上下限评估

| 能力维度 | 成熟度 | 上限（最佳情况） | 下限（最差/已知限制） | 关键影响因素 |
|---------|--------|----------------|---------------------|-------------|
| **文档解析** | 高 | 多引擎组合（DocReader+MinerU+anydoc+OCR）覆盖几乎所有格式，扫描 PDF 可 OCR，表格/公式结构化输出 | 无 DocReader/anydoc 时仅能解析纯文本（md/txt/csv），扫描 PDF 提取空内容 | 部署形态、OCR/VLM 引擎配置、文件类型 |
| **文档切片** | 高 | 三级自适应策略（标题感知→启发式→递归），父子分块+ContextHeader，受保护内容完整，表格表头传播 | 纯无结构文本只能递归硬切，超大受保护块（>7500字符）被强制截断 | 文档结构质量、切片策略选择、ChunkSize/Overlap 配置 |
| **图谱构建** | 中 | 强 LLM 下实体/关系抽取准确，开放域关系类型，Neo4j 可视化（概览/ego图/节点详情），Chunk 关联图增强检索 | 弱 LLM 下幻觉严重、实体重名合并错误，纯 LLM 无规则兜底，Neo4j 未启用时整个功能跳过 | LLM 模型能力、Neo4j 是否启用、文档领域明确度 |
| **检索能力** | 高 | 多模式混合（向量+关键词+图谱+Web）+ RRF 融合 + Rerank 精排 + MMR 去重 + 多存储扇出，FAQ 专用优化路径 | 只有纯向量检索时关键词匹配弱，无 Rerank 时长尾查询差，跨模型不可比 | Embedding/Rerank 模型质量、向量数据库后端、混合检索配置 |
| **Wiki 本体建模** | 中高 | 强 LLM 下双层本体（L1/L2）分类合理、粒度一致，法规场景专业适配，可追溯来源，多文档增量积累，Agent 可交互编辑 | 弱 LLM 下粒度不一致、分类错误、关系幻觉，只到 L2 不深入 L3，无本体推理，O(n²) 关系抽取成本高 | LLM 模型能力、摄入文档数量、场景模式（通用/法规）、抽取粒度配置 |

**核心结论**：工程化能力（解析/切片/检索）成熟度高、下限有保障；LLM 驱动能力（图谱/本体/关系）上下限差距大，质量完全依赖模型能力。

## 三、各升级项详细说明

### 3.1 Wiki 去重别名匹配增强（Phase 1，优先级最高）

**背景**：v0.8.2 官方对 `WikiDeduplicationPrompt` 做了大幅增强，直接影响 Wiki 本体的去重质量。

**核心改动**：
1. 新增完整的 "How to use names and aliases" 章节
2. **四向交叉比对**：name-to-name、name-to-alias、alias-to-name、alias-to-alias
3. **合并条件从 2 条增为 3 条**，且从"任一满足"改为"全部满足"
4. 新增**反歧义约束**：共享缩写不足以证明同一实体
5. 新增 3 个正反示例
6. 主名称不必相同也可合并（通过别名匹配）

**迁移要点**：
- 当前项目的去重提示词已中文化，需在中文基础上融合新增逻辑
- 保留 L2 粒度一致性原则（我们的本体约束）
- 新增的四向比对、反歧义约束等要中文化后写入

---

### 3.2 Wiki 页面续写机制（Phase 1）

**背景**：Wiki 页面重写时，LLM 输出长度可能不够导致内容截断，v0.8.2 新增自动续写机制。

**核心改动**：
1. 新增 `WikiPageModifyContinuationPrompt`（续写提示词）
2. 新增 `generateWithTemplateResult` 函数，检测输出是否截断
3. 最多 3 轮续传，仍截断则拒绝写入（`errWikiPageRewriteTruncated`）
4. `generateWithTemplate` 重构为薄包装，内部调用 `generateWithTemplateResult`

**迁移要点**：
- 需新增提示词并中文化
- `wiki_ingest.go` 中需新增 `generateWithTemplateResult` 和续写循环逻辑
- 我们的 `generatePageRelations` 在 finalize 阶段调用，与续写机制不冲突
- **不全量替换 wiki_ingest.go**（避免基础设施不兼容），只增量移植续写相关函数

---

### 3.3 Neo4j SearchNode 重构 + 防爆限制（Phase 1）

**背景**：v0.8.2 对 Neo4j 的 SearchNode 做了重构和性能加固。

**核心改动**：
1. **拆分三函数**：`graphSearchCypher`（构建查询）+ `decodeGraphSearchResult`（解析结果）+ `decodeGraphNode`（解码节点）
2. **搜索防爆限制**：`graphSearchMaxSeedNodes=200`（种子节点上限）、`graphSearchMaxRows=2000`（结果行上限）
3. **结果去重改用 ElementId**：从 name 改为 Neo4j 原生 ElementId，更准确
4. 排序策略优化：精确匹配优先 → 名称短优先 → 字母序优先
5. 超过限制打 warn 日志，不静默丢数据

**迁移要点**：
- 以 v0.8.2 的 `repository.go` 为基线
- **保留我们的节点重复创建 Bug 修复**（apoc.merge.node 匹配键修改）
- 重新追加我们的 6 个可视化查询方法：
  - `GetGraphOverview`（概览）
  - `GetEgoGraph`（ego 图）
  - `SearchGraphNodes`（节点搜索）
  - `GetGraphStats`（统计）
  - `GetRelationTypes`（关系类型）
  - `GetNodeDetail`（节点详情）
- 验证现有调用方（service/handler）接口签名是否兼容

---

### 3.4 Wiki 摄入 panic 恢复（Phase 2）

**背景**：v0.8.2 新增 `mapOneDocumentRecovered`，单文档 map 阶段 panic 不会搞垮整个进程。

**核心改动**：
- 在 `wiki_ingest_batch.go` 中新增 panic recover 包装
- 单个文档失败不影响其他文档

**迁移要点**：
- 改动量小，增量移植即可

---

### 3.5 实体提取更大输出预算 + OCR 文本（Phase 2）

**背景**：v0.8.2 增大了实体提取的输出 token 预算，并支持 OCR 文本参与提取。

**迁移要点**：
- 检查提取相关的 prompt 和配置参数
- 确认当前项目是否已有类似优化，没有则增量移植

---

### 3.6 Wiki 跨 KB 搜索（Phase 2）

**背景**：v0.8.2 新增 `SearchPagesAcross` 方法，支持多知识库联合搜索 Wiki 页面。

**核心改动**：
- `WikiPageService` 新增 `SearchPagesAcross` 方法
- `WikiPageRepository` 新增 `SearchAcross` 方法（多 KB + SQLite 兼容）
- 新增 Handler 和路由

**迁移要点**：
- 纯新增功能，不影响现有逻辑
- 我们现有的 Wiki 关系查询接口不受影响

- ElementId 去重：搜索结果不重复

### 5.4 回归测试
- 大文件上传正常
- 文档解析/切片正常
- 检索功能正常
