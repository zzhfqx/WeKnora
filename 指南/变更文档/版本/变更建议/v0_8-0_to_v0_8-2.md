### 2.2 改进与 Bug 修复（与我们相关的）

| 改进项 | 说明 | 对我们的影响 |
|-------|------|-------------|
| **上传超时动态计算** | `uploadTimeoutMs(data)` 根据 payload 大小计算 | ✅ 官方已覆盖，我们的修改可被替代 |

| **实体提取更大输出预算 + OCR 文本** | 提取更充分 | ✅ 改进，利好 |

### 2.3 不兼容变更（Breaking Changes）

| 变更 | 影响 |
|-----|------|
| 钉钉频道仅支持 Stream 模式 | 如不使用钉钉 IM 则无影响 |
| 沙箱命令默认以 `root` 执行 | 安全策略调整，不影响我们的核心功能 |
| `.env.example` 移除默认 `JWT_SECRET` / `SYSTEM_AES_KEY` | 部署配置需注意，现有部署要保留旧密钥 |
| 组织邀请按精确 workspace ID 搜索 | 如不使用多组织功能则无影响 |

## 四、关键风险点

### ⚠️ 风险 1：Migration 编号冲突
- 我们的 `000093_wiki_page_relations` 与官方的 `000093_browser_authorization` 冲突
- **解决**：重新编号为 `000115_wiki_page_relations`（紧跟官方最新的 `000114`）

### ⚠️ 风险 2：`wikiIngestService` 结构调整
- v0.8.2 中 `wikiIngestService` 不再直接持有 `*gorm.DB`
- 我们的 `generatePageRelations` 函数依赖 `s.db` 进行数据库操作
- **解决**：需要通过 `knowledgeRepo` 接口扩展，或在 `wikiIngestService` 中新增 `db` 字段并通过依赖注入传入

### ⚠️ 风险 3：模型层大重构
- v0.8.2 的 `internal/models/` 目录结构变化很大（新增 `catalog/`、`api/`、`providers/`、`runtime/` 等）
- 我们的提示词调用 `modelService.GetChatModel()` 接口签名可能有变化
- **需验证**：`GetChatModel` 的返回类型和使用方式是否兼容

### ⚠️ 风险 4：`KnowledgeBase.vue` 大幅重构
- v0.8.2 中从 4547 行减到 3433 行（减了约 24%）
- 我们的 Neo4j Graph Tab 插入逻辑需要重新定位
- **需验证**：tab 管理方式是否变化

## 五、升级建议

### 📊 综合评估

| 维度 | 评分 | 说明 |
|-----|------|------|
| **升级必要性** | ⭐⭐⭐ 中 | 没有我们急需的功能，但有重要 Bug 修复和安全改进 |
| **升级工作量** | ⭐⭐⭐ 中（约 2-3 人天） | 主要工作量在 Wiki 关系抽取适配 + migration 编号 + Neo4j 可视化重新接入 |
| **风险可控性** | ⭐⭐⭐⭐ 高 | 核心修改点都在独立模块，冲突范围可预期 |

### ✅ 推荐升级，理由：

1. **安全加固**：白名单出站模式、多项 RBAC 修复、SSRF 加固，对于生产环境有价值
2. **官方 Bug 修复**：文档卡死在 processing/deleting 状态、跨工作区访问漏洞等多项修复
3. **性能改进**：更快的分块摄入、关键词检索优化、Neo4j 搜索限制（防爆炸）
4. **上传改进**：官方动态超时比我们的固定超时更合理
5. **模型目录重构**：27 家厂商自动补全能力，后续接入新模型更方便
6. **前瞻性**：v0.8.2 是当前最新版，后续官方迭代将基于此分支

### ⏳ 可以暂缓升级的情况：

- 当前版本运行稳定，没有遇到 v0.8.2 修复的具体 Bug
- 短期内没有使用新功能（本地浏览器、内置 MCP Server、对话分叉等）的需求
- 项目处于关键交付期，不宜引入变动

## 六、升级操作步骤（精简版）

详细步骤参考变更记录文档第八章，以下是针对 v0.8.2 的调整：

### Step 0：准备
- 备份当前分支代码
- 确认 v0.8.2 源码完整

### Step 1：替换源码 + 修正基础
1. 将 v0.8.2 源码作为新基线
2. 重新编号 `wiki_page_relations` migration：`000093` → `000115`
3. 应用开发模式改进（端口偏移、后台脚本、Makefile 等）

### Step 2：Wiki 本体改造移植
1. **提示词**：以 v0.8.2 的 `prompts_wiki.go` 为基础，将我们的中文版提示词（L1/L2 架构）替换进去，并**中文化新增的 `WikiPageModifyContinuationPrompt` 和去重别名逻辑**
2. **关系抽取适配**：
   - 确认 `wikiIngestService` 中 db 的获取方式
   - 如有必要，通过构造函数注入 `*gorm.DB`
   - 将 `generatePageRelations` 函数移植过去
3. **关系查询 API**：移植 `GetPageRelations` 到新版 service 和 handler
4. **路由 + 依赖注入**：注册路由和 Provide
5. **类型定义**：复制 `WikiPageRelation` 结构体和接口

### Step 3：Neo4j 图谱可视化移植
1. 确认 `neo4j/repository.go` 路径（`internal/application/repository/retriever/neo4j/`）
2. **保留节点去重 Bug 修复**（这是核心，官方没修）
3. 追加我们的可视化查询方法（`GetGraphOverview`、`GetEgoGraph` 等）
4. 复制新增的 Service、Handler、类型定义、接口文件
5. 注册路由和依赖注入
6. 前端：移植 `Neo4jGraphViewer.vue` + API 扩展
7. 在新版 `KnowledgeBase.vue` 中找到 Tab 定义位置，加入 `neo4j-graph` tab

### Step 4：大文件上传
- 前端上传超时：v0.8.2 已有动态超时，我们的修改可以移除或保留
- 失败提示：保留我们的增强
- 后端日志：选择性保留

### Step 5：别名编辑功能
- 移植 WikiBrowser.vue 中的别名编辑 UI
- 同步各语言 locale 文件

### Step 6：验证
1. 数据库迁移（`000115`）
2. 启动后端，检查日志错误
3. 验证核心功能：Wiki 提取、关系抽取、Neo4j 图谱、大文件上传
4. 验证所有原有改动仍然生效

## 七、总结

**建议升级**。v0.8.2 虽然没有我们急需的颠覆性新功能，但包含了大量 Bug 修复、安全加固和性能改进，且官方后续迭代将基于此分支。升级的主要工作量集中在 Wiki 关系抽取的结构适配（约半天）和 Neo4j 可视化的重新接入（约 1 天），其余改动均可快速移植。总体预计 **2-3 人天** 可完成升级并通过验证。
